---

PostgreSQL 通常为每个客户端连接创建独立后端进程。大量空闲连接会占用内存和进程资源，大量活跃连接则增加 CPU 调度、锁和 I/O 竞争。连接池的价值是复用后端并限制数据库并发。

## 两层连接池

应用内连接池复用本进程连接；PgBouncer 等外部池可以让更多客户端连接共享较少 PostgreSQL 后端。两层都需要上限，避免应用实例扩容后把外部池的等待队列撑满。

数据库总预算还要预留管理、迁移、复制、Autovacuum 和故障切换空间。不能把 `max_connections` 全部分给在线应用。

## PgBouncer 池模式

| 模式 | 后端分配时间 | 主要兼容性 |
| --- | --- | --- |
| Session | 整个客户端会话 | 会话状态兼容最好，复用率最低 |
| Transaction | 一个事务 | 常用折中，事务外不能依赖固定后端 |
| Statement | 一条语句 | 限制最多，不支持多语句事务 |

事务池模式下，会话级临时表、会话级咨询锁、`LISTEN`、部分 `SET` 状态以及依赖后端会话的功能可能失效或泄漏。协议级预处理语句兼容性取决于 PgBouncer 版本与配置，升级前应根据驱动真实行为测试。

使用事务级 `SET LOCAL` 把状态限制在事务中，或在连接建立和归还时使用受支持的重置策略。不能假设下一条语句仍在同一后端进程执行。

## 事务边界

事务池只有在客户端提交或回滚后才能释放后端。`idle in transaction` 会同时持有后端、锁和旧快照，是高风险状态。

为连接获取、语句、锁等待和 idle transaction 设置有界超时。超时后客户端必须回滚；不能把失败事务直接放回应用连接池。

## 连接预算和排队

通过负载测试找到数据库在目标延迟下的有效活跃连接数。PgBouncer 的默认池、每用户池、保留池和客户端上限都应围绕该预算设置。

等待队列要有时间上限。池满时快速失败比让所有请求占据工作线程更容易恢复。监控客户端连接、活跃/空闲后端、等待客户端、等待时间、事务速率和数据库 CPU。

## 故障与维护

数据库重启或主从切换后，旧连接会失败。池需要刷新地址、关闭失效连接并限制重连速率。连接代理不能判断未收到响应的事务是否已经提交，写操作重试仍需幂等键或业务查询。

计划维护前先验证暂停、排空和恢复命令对现有事务的行为。证书、密码和 DNS 轮换应保留重叠窗口，让连接按最大生命周期逐步更新。

## 验证清单

- 正常峰值下没有持续等待，数据库仍有运维预留连接。
- 扩缩容和滚动发布不会超过总连接预算。
- 事务池模式下的驱动预处理、会话变量和迁移工具行为正确。
- 数据库慢或不可用时，请求在截止时间内失败且不会形成重连风暴。
- 应用名称、用户和数据库维度能够关联 PgBouncer 与 `pg_stat_activity`。
