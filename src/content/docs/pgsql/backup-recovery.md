PostgreSQL 备份分为逻辑备份和物理备份。选择取决于数据量、恢复粒度、版本迁移、RPO 和 RTO。复制不是备份：误删除和逻辑损坏会迅速传播到副本。

## 逻辑备份

`pg_dump` 导出单个数据库中的对象和数据，并在一致性快照中工作：

```bash
pg_dump --format=custom --file=app.dump app
pg_restore --jobs=4 --dbname=app_restore app.dump
```

自定义或目录格式支持选择对象和并行恢复。全局角色、表空间等集群对象需要通过 `pg_dumpall --globals-only` 等方式单独处理。

逻辑备份适合对象级恢复和跨版本迁移，但大库恢复通常较慢，恢复期间还要重建索引、约束和统计信息。导出时间很长时，旧快照也可能影响 VACUUM。

## 物理备份与 WAL

物理基础备份复制整个数据库集群的数据文件，并依赖 WAL 保证一致性。可以使用 `pg_basebackup`、备份工具或经过一致性设计的存储快照。

PITR 需要：

1. 一个可恢复的物理基础备份。
2. 从该备份开始到目标时间点之间连续、完整的 WAL 归档。
3. 恢复所需的版本、配置、扩展库和密钥。

任何 WAL 缺口都会中断恢复链。复制槽不是 WAL 归档方案；槽失去消费者时还可能让 `pg_wal` 无限增长。

## 时间点恢复流程

1. 在隔离环境恢复基础备份。
2. 配置 `restore_command` 从归档取回 WAL。
3. 设置目标时间、事务或恢复点，并启动 PostgreSQL 重放。
4. 检查恢复是否到达预期目标，确认时间线分叉。
5. 校验关键表、业务汇总、权限、扩展和序列。
6. 通过受控方式切换应用流量。

恢复配置字段随 PostgreSQL 版本演进，应严格使用目标版本文档。目标时间要写明时区，事故时最好使用预先创建的命名恢复点或事务证据。

## 安全与保留

- 将备份与 WAL 放在不同账号、区域或不可变存储中。
- 加密传输和静态数据，并定期验证密钥恢复。
- 备份中包含生产敏感数据，访问和脱敏要求不能降低。
- 保留策略必须覆盖最长检测延迟和目标恢复窗口。
- 监控归档失败、WAL 积压、备份时长、备份大小和最近成功恢复时间。

## 恢复演练

定期自动选择历史备份并恢复，记录下载、解密、WAL 重放、启动和数据校验耗时。使用应用只读检查或抽样查询验证业务语义，不能只确认端口可连接。

升级大版本、扩展或备份工具后重新演练。RTO 应来自最近一次同规模恢复的测量，而不是备份任务“成功”所用的时间。
