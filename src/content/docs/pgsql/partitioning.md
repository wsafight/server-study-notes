---
title: PostgreSQL 声明式分区设计
description: 设计 PostgreSQL Range、List 和 Hash 分区，并评估裁剪、索引、约束与分区生命周期。
---

分区把一张逻辑表拆成多个物理关系，主要价值是数据生命周期管理、按分区维护，以及在查询条件包含分区键时减少扫描范围。分区不会自动让所有大表查询更快。

## 选择分区键

- Range 适合时间、连续编号和按周期归档的数据。
- List 适合数量稳定的地区、业务域或租户组。
- Hash 可以均匀分散写入，但不便按业务范围删除和归档。

分区键应出现在大多数高成本查询和生命周期操作中。仅因为表很大就按日期分区，而查询从不限制日期，通常只会增加规划和维护成本。

## 创建时间分区

```sql
CREATE TABLE event_log (
    tenant_id bigint NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload jsonb NOT NULL,
    PRIMARY KEY (tenant_id, occurred_at)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE event_log_2026_08
PARTITION OF event_log
FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
```

上下界采用左闭右开，避免相邻分区重叠。时间边界应明确时区，不要让会话时区隐式决定分区归属。

## 分区裁剪

规划器只有能从条件推导出分区键范围时才能裁剪。对分区键包装不透明函数、混用类型或缺少范围条件，可能访问更多分区。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM event_log
WHERE occurred_at >= timestamptz '2026-08-01 00:00:00+00'
  AND occurred_at <  timestamptz '2026-08-02 00:00:00+00';
```

检查计划实际访问了哪些分区。Prepared Statement 和运行期参数可能触发执行期裁剪，需要结合实际执行验证。

## 索引与唯一性

父表上的分区索引会在各分区维护对应子索引，但每个索引仍是独立物理对象。分区表上的唯一约束通常必须包含所有分区键，因为数据库需要在不扫描所有分区的情况下保证唯一性。

如果业务要求全局唯一但分区键不在唯一键中，可以调整标识生成方式、重新选择分区键，或使用独立登记表承担唯一性边界。不要假设各分区分别唯一等于全表唯一。

## 生命周期管理

提前创建未来分区，并监控默认分区是否意外吸收数据。归档旧数据时，Detach 或 Drop 分区通常比逐行删除产生更少 WAL 和膨胀，但仍需评估元数据锁、外键和并发查询影响。

新分区需要同步验证：

- 所有必要索引、约束和权限是否存在。
- Autovacuum 和统计参数是否继承了预期配置。
- 备份、复制、归档和监控是否发现新对象。
- 写入边界值是否进入正确分区。

## 避免过度分区

分区过多会增加规划时间、系统目录对象、连接上的锁对象和运维复杂度。按小时、租户和业务类型多层组合前，应使用真实保留周期计算最终分区数量。

分区粒度应匹配最常见的清理单位和查询范围。对长期冷数据，也可以通过分层存储或导出到 Parquet，再使用 DuckDB 等分析引擎查询，避免让在线事务库长期承担全部历史扫描。

## 上线验证

使用边界日期、跨分区查询、缺少分区条件的查询和未来日期写入做测试。记录规划时间、访问分区数、Buffers、WAL 和清理耗时，确认收益来自可测量的裁剪或维护简化。
