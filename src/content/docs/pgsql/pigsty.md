title: 使用 Pigsty 部署 PostgreSQL
description: 介绍 Pigsty 的 PostgreSQL 高可用、监控、备份能力和采用前的评估要点。
---

[Pigsty](https://pigsty.io/) 是一个开源、基于声明式配置和自动化编排的 PostgreSQL 发行版。它把数据库部署、高可用、监控、备份和常用扩展整合为一套可重复执行的运维方案。

## 核心能力

- 使用自动化配置部署单机或高可用 PostgreSQL 集群。
- 集成服务发现、连接池或代理、故障切换和只读副本。
- 提供 Prometheus 与 Grafana 监控体系，覆盖数据库、操作系统和连接层。
- 集成备份、归档和按时间点恢复所需组件。
- 管理常用 PostgreSQL 扩展，并提供预定义的角色和访问控制配置。

具体组件和默认值会随 Pigsty 版本变化，部署前应以目标版本的官方文档为准。

## 适用场景

- 团队希望自建 PostgreSQL，但不想从零组合高可用、监控和备份体系。
- 需要在多套环境中重复部署一致的数据库集群。
- 希望对数据库基础设施拥有更多配置和数据控制权。
- 需要集中管理多个 PostgreSQL 实例与扩展。

## 采用前评估

1. 明确节点、网络、操作系统和磁盘的支持范围。
2. 验证故障检测、主库切换、客户端重连和脑裂保护。
3. 完成全量备份、WAL 归档、PITR 和异地恢复演练。
4. 评估升级 Pigsty、PostgreSQL 和扩展时的兼容路径。
5. 定义监控告警、值班责任、容量模型和安全基线。

## 先设计数据库拓扑

自动化工具不会替代拓扑决策。部署前明确：

- 主库、同步副本、异步副本和灾备节点分别承担什么目标。
- 应用通过哪个稳定入口连接，读写和只读流量如何区分。
- 故障切换由谁触发，如何防止旧主库重新接受写入。
- 节点、可用区、网络和存储故障是否会同时影响多个副本。
- RPO、RTO 与同步提交、备份频率和异地归档是否一致。

不要把“节点数量达到三台”直接等同于高可用。共同电源、网络、存储或控制面仍可能形成单点。

## 分阶段上线

1. 在隔离环境生成 Inventory 和配置，审查账户、端口、目录、系统参数与软件源。
2. 部署测试集群，导入近似数据和扩展，建立性能与容量基线。
3. 验证监控、告警、日志、备份、WAL 归档和证书轮换。
4. 分别模拟 PostgreSQL 进程、节点、网络和存储故障。
5. 让真实客户端经历主库切换，确认 DNS、代理、连接池和事务重试行为。
6. 完成全量恢复与时间点恢复后，再评估生产切入。

自动化执行成功只说明期望配置被应用，不说明业务已经能容忍故障切换。

## 日常运维

将 Pigsty 配置、PostgreSQL 参数和人工变更纳入同一变更流程，避免下一次自动化执行覆盖现场修复。持续检查配置漂移、备份新鲜度、归档失败、复制槽保留、证书到期、磁盘增长和扩展版本。

升级时分别考虑操作系统、Pigsty、PostgreSQL 大版本、小版本和扩展。先验证支持矩阵与回滚条件，再滚动执行；数据库大版本升级仍需要专门的数据兼容和停机方案。

## 安全与退出路径

限制自动化控制节点、配置仓库、备份存储和监控系统的访问。配置中的密钥应由受控 Secret 机制提供，不进入普通 Git 历史或日志。

保留标准 PostgreSQL 工具可读取的备份和清晰的集群配置说明。演练在没有原控制节点或原软件仓库的情况下恢复数据库，避免基础设施工具本身成为无法退出的依赖。

Pigsty 可以减少基础设施组装工作，但不会替代 PostgreSQL 运维能力。生产使用仍需要理解[复制](../replication/)、WAL、事务、锁、[备份恢复](../backup-recovery/)和容量规划。
