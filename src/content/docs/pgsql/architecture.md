PostgreSQL 使用客户端/服务端架构。客户端连接通常对应一个后端进程；在大量短连接场景中，常通过 PgBouncer 等连接池限制数据库后端数量。

## 主要组件

- **Postmaster：** 监听连接、创建后端进程并管理辅助进程。
- **Backend：** 解析、规划并执行某个会话的 SQL，维护事务和会话状态。
- **Shared Buffers：** 缓存数据库页面，并协调多个进程访问。
- **WAL Buffers：** 暂存预写日志记录，提交与检查点按配置将其刷入持久化存储。
- **Background Writer 与 Checkpointer：** 协助写出脏页并创建恢复检查点。
- **Autovacuum：** 回收可复用空间、更新可见性信息并防止事务 ID 回卷。
- **WAL Sender/Receiver：** 在物理复制中传输 WAL。

操作系统页缓存仍参与文件 I/O，因此不能简单把 `shared_buffers` 设置为全部内存。连接、排序、哈希、维护任务和扩展也会消耗内存。

## 一次查询如何执行

1. 解析器检查语法并生成语法树。
2. 分析与重写阶段解析对象、类型、权限、规则和视图。
3. 优化器根据统计信息估算多个访问路径的成本。
4. 执行器运行选定计划，通过访问方法读取堆表或索引。
5. 修改操作生成 WAL，并产生可供 MVCC 管理的新行版本。

优化器成本是抽象估算值，不等于毫秒。统计信息不准确、列之间存在相关性或参数分布差异时，估算可能明显偏离实际值。

## 表、页面与行版本

普通表的行版本存放在堆文件页面中，索引条目指向对应的堆元组。更新通常创建新行版本，并让旧版本在之后由 VACUUM 处理；满足 HOT 条件的更新可以避免修改不相关索引。

这种设计支持 MVCC，但长事务、失效复制槽和不及时的 VACUUM 会阻止旧版本回收，造成表与索引膨胀。

## WAL 与提交

WAL 遵循先写日志再写数据页的原则。崩溃恢复从最近检查点开始重放 WAL，使数据文件回到一致状态。流复制和时间点恢复也依赖连续 WAL。

事务提交返回的耐久性受 `synchronous_commit`、WAL 刷盘、复制配置和存储系统影响。同步复制可以等待指定同步节点达到某个阶段，但会增加提交延迟，并需要处理同步节点不可用时的行为。

## Schema 与系统目录

一个数据库中可以包含多个 Schema，未限定名称会按 `search_path` 解析。应用应固定并审查 `search_path`，避免对象遮蔽和权限问题。

表、索引、类型、函数和权限等元数据存储在系统目录中，可通过 `pg_catalog` 与 `information_schema` 查询。不要直接修改系统目录；使用 DDL 和官方维护工具。

理解这些边界后，性能排查可以围绕计划估算、Buffer/WAL、行版本、锁和连接数收集证据，而不是只依赖一条“慢 SQL”。
