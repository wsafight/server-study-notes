---
title: Linux 系统化故障排查
description: 通过时间线、影响范围、USE 方法和逐层验证，从告警快速收敛到可证明的原因。
---

有效排障需要把“服务很慢”转化为可验证的问题。先保护现场和业务，再从用户请求向应用、操作系统、虚拟化与硬件逐层收集证据。

## 1. 定义现象

先记录以下信息：

- 首次发生时间、持续时间、频率和时区。
- 受影响的接口、租户、可用区、实例和请求比例。
- 延迟是排队、连接、服务端处理还是下游等待。
- 故障前后的发布、配置、流量、定时任务和基础设施事件。
- 当前错误率、吞吐和业务降级状态。

使用同一时钟把应用追踪、系统日志和监控指标对齐。时钟漂移会让因果顺序看起来相反。

## 2. 做快速系统快照

下面的命令开销通常较低，但仍应按环境控制采样时间：

```bash
date -Ins
uptime
free -h
vmstat 1 10
mpstat -P ALL 1 10
pidstat -u -r -d -w 1 10
iostat -xz 1 10
ss -s
```

同时保存内核和服务日志，而不是只截取最后一行错误。容器环境还要记录 Pod 限额、重启原因、节点压力和 cgroup 指标。

## 3. 使用 USE 方法

对 CPU、内存、磁盘、网络和配额逐一检查：

- **Utilization：** 资源忙碌或已使用的比例。
- **Saturation：** 是否出现排队、等待或超限。
- **Errors：** 是否存在硬件、内核、协议或应用错误。

例如 CPU 利用率不高但运行队列持续增长，可能受到 cgroup CPU quota 限制；磁盘吞吐不高但 `await` 上升，可能存在随机 I/O、设备错误或共享存储争用。

## 4. 收敛到进程和操作

用 `pidstat` 找到异常进程或线程，再将 PID 对应到服务、容器、请求和最近发布。需要进一步确认时按层选择工具：

- CPU 热点：`perf top` 或有限时长的 `perf record`。
- 系统调用阻塞：短时间 `strace -p <pid>`，注意性能与敏感数据。
- 文件占用：`lsof -p <pid>` 或检查 `/proc/<pid>/fd`。
- 网络连接：`ss -tpn`，必要时在批准范围内抓包。
- 内存映射：`pmap -x <pid>`、`/proc/<pid>/smaps_rollup`。

不要因为看到某进程占用最高就立即判定它是根因。它可能只是处理了更多流量，也可能在等待真正故障的下游。

## 5. 验证假设

每次只提出可被反驳的假设，例如“磁盘延迟使工作线程排队”。然后明确预期证据：I/O `await`、进程块 I/O、请求跨度和设备错误应在同一时间上升。

执行缓解操作前记录基线。操作后观察相同指标和完整业务周期，确认是因果改善而不是流量自然下降。

## 6. 沉淀复盘

复盘至少包含影响、时间线、触发条件、放大因素、为何未提前发现、缓解与长期修复。把临时命令整理为有限时长、可脱敏的采集脚本，并为关键资源建立容量趋势和告警。

重启可以恢复服务，但会清除部分现场。若业务允许，先采集最小证据包；若必须立即止损，也应明确记录重启前后的变化，避免把“重启有效”误写成根因。
