---
title: 排查 Linux 网络问题
description: 从 DNS、连接建立、TCP 重传、网卡错误和应用延迟逐层定位网络故障。
---

“网络超时”可能发生在 DNS、连接建立、TLS、请求排队、服务端处理或响应传输任一阶段。先用应用追踪或分阶段计时确认慢在哪里，再检查对应的网络层。

## 建立连接视图

```bash
ss -s
ss -lntp
ss -tan state established
ip -s link
ip route
```

检查服务是否监听预期地址和端口、连接状态是否异常堆积、路由是否正确，以及网卡是否出现 drop、error。容器环境还需检查 Service、Ingress、网络策略和节点连接跟踪表。

`TIME-WAIT` 是 TCP 正常状态，数量多本身不是故障。应结合连接创建速率、端口范围、客户端是否复用连接以及请求错误判断。

## 连续采样协议指标

安装 `sysstat` 后可以观察设备、TCP 连接和错误：

```bash
sar -n DEV 1 10
sar -n TCP,ETCP 1 10
```

重点对比历史基线：

- 网卡吞吐是否接近实际链路或实例带宽上限。
- 丢包、错误、重传和被动连接失败是否同时上升。
- TCP 重传是客户端、服务端还是中间链路触发。
- 接收或发送队列是否持续积压。

重传是端到端现象，不能仅凭一台主机的计数确定故障位置。

## 分解一次请求

```bash
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com/health
```

这能粗略区分 DNS、TCP、TLS 和首字节时间，但测试路径、代理、连接复用和目标接口必须与真实请求一致。DNS 问题还应检查解析结果、TTL、本机缓存和多个上游服务器。

## 队列与连接上限

连接拒绝或超时可能来自应用 accept 不及时、监听队列过小、文件描述符不足、连接池耗尽、防火墙或 conntrack 表压力。检查时同时查看：

- 应用工作线程、连接池和请求队列。
- `ulimit -n` 与进程当前文件描述符数量。
- `ss -lnt` 的监听队列。
- 内核日志中的 conntrack、驱动或链路错误。

不要直接扩大所有队列。更大的队列可能只是把快速失败变成更长尾延迟。

## 谨慎抓包

当指标不足以解释握手、重传或协议问题时，可在明确接口、主机、端口和持续时间后使用 `tcpdump`。抓包可能包含账号、Token 和业务数据，必须限制文件大小、访问权限和保存时间。

最终结论应能把客户端错误、服务端连接状态、网络计数和中间设备事件对齐到同一时间段。单次 `ping` 成功只能说明特定 ICMP 路径当时可达，不能证明应用协议正常。
