DuckDB 可以把表、Schema 和元数据保存在单个数据库文件中，但活跃数据库还涉及进程内状态、WAL、临时目录和扩展。可靠运维必须围绕数据库 Owner Process 和明确的静止点设计，不能把复制一个正在写入的文件当作完整备份。

## 明确所有权与恢复目标

先为每个持久数据库定义：

- 哪个进程拥有写权限，哪些进程只能读。
- 数据库文件、WAL、Secret 和临时目录分别位于哪里。
- 数据可以从哪些源文件或上游快照重建。
- 可接受的数据丢失量（RPO）和恢复时间（RTO）。
- DuckDB 核心、客户端绑定、扩展和平台版本。

如果数据库只是可重建缓存，恢复流程可以删除损坏副本并从输入 Manifest 重算。如果它保存唯一数据，备份频率、异地副本和恢复演练必须按有状态数据库设计。

数据库文件优先放在具有受支持锁和持久化语义的本地文件系统。容器重建、临时卷、网络共享盘和同步网盘都可能改变持久性或锁行为，必须在目标环境验证。

## 理解 WAL 与 Checkpoint

事务提交后，变更可能先存在 WAL 中，再由 Checkpoint 合并进主数据库文件。不要手工删除、移动或截断伴随文件，也不要根据文件名判断它已经无用。

受控维护窗口可以主动执行：

```sql
CHECKPOINT;
```

Checkpoint 会产生 I/O，并可能受到活跃事务影响。执行前限制新写入，设置任务截止时间，监控数据库目录可用空间和延迟；不要在磁盘已经接近满时把它当作无成本清理命令。

数据库文件、WAL 和临时目录都要纳入磁盘告警。长事务、批量写入、失败重试和大查询 Spill 可能同时占用空间。磁盘满测试应验证事务返回错误、进程重启后能够恢复，以及发布任务不会暴露部分外部文件。

## 选择备份方式

备份必须来自一致性边界，常见方式有两类。

第一类是在 DuckDB 中导出逻辑快照：

```sql
EXPORT DATABASE 'backups/analytics-2026-08-26'
(FORMAT parquet);
```

导出目录包含重建 Schema 和数据所需的文件，便于检查和跨环境恢复，但会扫描并写出数据库内容，需要足够时间与空间。视图、序列、扩展类型和其他对象的覆盖范围应在目标版本逐项验证。

第二类是文件级副本。先阻止新写入并等待所有写事务完成，关闭持有数据库的连接，在受控情况下完成 Checkpoint，再复制明确的数据库文件和目标版本要求的伴随文件。文件复制完成后再恢复服务。不要直接复制一个持续写入中的文件，也不要只依赖文件系统快照却从未做恢复测试。

每份备份都记录：

- 生成时间、数据库逻辑版本和源任务高水位。
- DuckDB、客户端与扩展版本及操作系统架构。
- 备份方式、文件列表、大小和校验和。
- 加密、访问权限、保留期和恢复说明。
- 最近一次恢复演练的结果。

Secret 和云身份通常不应随数据库备份复制。恢复环境通过自己的 Secret 管理重新配置最小权限凭据。

## 执行恢复演练

逻辑导出可以导入一个新的空数据库：

```sql
IMPORT DATABASE 'backups/analytics-2026-08-26';
```

不要直接覆盖当前生产文件来“测试恢复”。在隔离目录创建新数据库，使用记录的版本打开，并验证：

- 所有预期 Schema、表、视图和宏存在。
- `DESCRIBE` 与声明的数据契约一致。
- 关键表行数、主键唯一性、金额和时间边界正确。
- 代表性查询能够执行，扩展可以从批准来源加载。
- 文件权限正确，非 Owner Process 无法写入。
- 恢复耗时和额外磁盘满足 RTO。

文件能打开只证明页和元数据足以启动，不能证明业务数据完整。恢复成功标准必须包含业务不变量和上游位点。

## 安全升级 DuckDB

升级前同时固定核心库、语言绑定和扩展，不要只记录 CLI 版本。准备真实数据库副本和代表性文件，在隔离环境执行以下流程：

1. 使用旧版本完成备份并验证可以恢复。
2. 用新版本只读打开副本，执行 Schema 和代表性查询。
3. 在另一个副本执行写入、Checkpoint、重启和故障恢复。
4. 比较结果类型、执行计划、性能、峰值内存和文件增长。
5. 验证所有扩展能够离线加载，外部 Catalog 和文件格式兼容。
6. 只在通过后安排写入静止点并升级 Owner Process。

新版本写入数据库后，旧版本未必能够重新打开或理解所有新特性。回滚方案应恢复升级前备份和对应程序版本，而不是让旧二进制继续写已经被新版本修改的唯一文件。

## 管理 Schema 迁移

持久表也需要版本化迁移。建立应用自己的迁移记录表，按顺序记录迁移 ID、查询版本、执行时间和校验结果。迁移前检查磁盘预算和锁影响；对大表重写，不要假设 `ALTER TABLE` 始终是元数据操作。

DuckDB 内部 DDL 与 DML 可以放在显式事务中：

```sql
BEGIN TRANSACTION;

ALTER TABLE orders ADD COLUMN source VARCHAR;
UPDATE orders SET source = 'legacy' WHERE source IS NULL;

COMMIT;
```

先在真实规模副本测量耗时、临时空间和文件增长。外部 Parquet 写出、对象存储请求和其他数据库中的变更不受这个事务回滚保护；涉及它们时使用分阶段发布和补偿流程。

破坏性变更采用 Expand and Contract：先增加兼容列或新表，回填并双读验证，再切换查询，经过回滚窗口后才删除旧结构。不要在同一次不可逆迁移中同时升级数据库版本、扩展和业务 Schema。

## 控制空间增长

删除或更新数据不表示数据库文件会立即缩小。内部页面可能留待后续复用，WAL、长事务和临时 Spill 也会让目录增长。定期记录数据库文件、WAL、临时目录和逻辑表数据量，区分可复用空间与持续泄漏。

`VACUUM`、统计维护和空间回收的具体行为随版本变化，不要把命令执行成功等同于操作系统文件已经缩小。确实需要压缩文件时，先在副本上比较目标版本支持的维护方法与“逻辑导出后导入新数据库”方案，再通过版本文件切换发布；保留旧文件直到新文件验证完成。

设置磁盘高水位后应停止接收新的重任务，保留完成回滚、Checkpoint 或诊断所需的余量。自动清理只能处理明确归属的过期临时目录和旧发布版本，绝不能通配删除活跃数据库旁的未知文件。

## 故障运行手册

至少演练进程强制终止、磁盘满、数据库目录只读、WAL 存在时重启、错误版本打开、扩展缺失和备份损坏。每种场景记录：

1. 如何检测并阻止新的写入。
2. 哪些文件必须原样保留用于诊断。
3. 何时选择正常恢复、恢复备份或从源数据重建。
4. 如何验证业务数据与外部发布结果一致。
5. 如何回退应用、数据库文件和扩展版本。

运维流程最终应能证明数据库在指定 RPO/RTO 内恢复，而不只是证明平时可以正常打开。
