DuckDB 是嵌入式数据库，连接运行在应用进程中，不是面向大量远程客户端的独立事务服务器。它支持 ACID 事务和并发读取，但部署边界与 PostgreSQL 等 Client-Server 数据库不同。

## 单进程并发模型

同一进程可以创建多个连接并并发查询。读取能够利用 DuckDB 的并行执行，多个线程同时提交互不冲突的变更也可以工作；冲突写入可能通过乐观并发控制失败，需要调用方回滚和重试。

不要根据应用线程数等量创建查询。单条分析查询本身就会使用多个执行线程，过多并发查询可能争夺相同 CPU、内存和临时磁盘。

建立任务队列或信号量，分别限制交互查询、批量导入和高内存任务。结合真实峰值内存设置进程并发，而不是只按连接数量限流。

## 显式事务

```sql
BEGIN TRANSACTION;

CREATE TEMP TABLE staged AS
SELECT *
FROM read_parquet('incoming/*.parquet');

DELETE FROM fact_sales
WHERE batch_id = '2026-08-26';

INSERT INTO fact_sales
SELECT * FROM staged;

COMMIT;
```

事务保护 DuckDB 数据库中的变更，不会回滚已经写出的外部 Parquet 文件、HTTP 请求或应用副作用。跨数据库文件和对象存储发布需要额外的 Manifest 或两阶段应用协议。

长事务会保留旧版本并延迟清理，还可能扩大内存和文件增长。读取、转换和外部下载可以先在事务外完成，最终替换步骤保持短小。

## 多进程访问

多个进程可以只读打开同一数据库文件；跨进程持续并发写入不是 DuckDB 的主要设计目标。操作系统文件锁能防止部分危险访问，但不能把嵌入式文件自动变成远程事务服务。

需要多进程写入时，常见选择是：

- 让一个 Owner Process 串行处理写请求。
- 每个 Worker 写独立数据库或 Parquet 分片，之后合并。
- 将在线写入放在 PostgreSQL 等服务端数据库，再用 DuckDB 分析快照。

共享网络文件系统还会引入锁和持久化语义差异，必须按目标存储验证，不要只在本地 APFS 或 ext4 测试。

## 数据库文件生命周期

单个数据库文件便于分发，但复制正在写入的文件不一定得到一致快照。优先在 DuckDB 内执行受支持的导出、备份或 Checkpoint 流程；完整备份、升级和恢复步骤参见[数据库文件运维](./database-operations/)。

进程崩溃后的恢复依赖数据库文件和 WAL 状态。不要手工删除看似临时的伴随文件。为数据库目录预留写权限和磁盘空间，并测试强制终止、磁盘满和进程重启。

## 只读服务与缓存

嵌入式报表服务可以按发布版本只读打开数据库文件，在新文件完全生成后切换指针。旧请求继续使用旧版本，新请求打开新版本，能避免在请求路径上执行大规模写入。

内存中的 DuckDB 适合短生命周期计算，但进程退出后不会持久化。缓存或临时结果必须能从可信输入重建。

## 验证场景

并发运行长查询、写入、Checkpoint 和应用退出，记录吞吐、峰值内存、临时磁盘、冲突错误与恢复时间。再测试多个独立进程误开同一文件，确保部署保护能快速失败并给出可诊断日志。
