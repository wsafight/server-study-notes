---
title: 建立服务可观测性体系
description: 使用指标、日志、追踪和持续剖析解释服务状态，并控制成本与高基数风险。
---

可观测性是根据系统外部输出推断内部状态的能力。目标不是收集尽可能多的数据，而是让工程师能够回答用户受到什么影响、从哪里开始、哪个组件改变以及修复是否有效。

## 四类主要信号

| 信号 | 适合回答 | 常见限制 |
| --- | --- | --- |
| 指标 | 发生多少、趋势如何、是否超出 SLO | 聚合后缺少单次请求上下文 |
| 日志 | 某个事件包含哪些字段和错误 | 数据量大、格式与采样不一致 |
| 追踪 | 一次请求经过哪些服务、时间花在哪里 | 采样可能遗漏低频异常 |
| 剖析 | CPU 时间、分配和锁竞争集中在哪里 | 需要控制持续时间和运行开销 |

四者应通过时间、服务、版本、实例和追踪标识关联，而不是建立四套互不相通的工具。

## 先覆盖请求主路径

对在线服务至少记录 RED 信号：

- **Rate：** 有效请求速率和工作量。
- **Errors：** 按业务语义分类的失败比例。
- **Duration：** 延迟分布，尤其是 P95、P99 等尾部。

对 CPU、内存、磁盘、网络、连接池和队列使用 USE 方法观察利用率、饱和度和错误。资源指标用于解释用户 SLI，而不是替代 SLI。

## 结构化日志

日志应包含稳定字段，例如时间、级别、服务、版本、环境、请求或追踪 ID、错误类型和业务操作，但不能记录密码、Token、完整身份信息或无必要的请求正文。

错误日志需要保留最初原因和调用链，不要在每一层重复输出相同堆栈。重试过程可以记录尝试次数和最终结果，避免一次故障生成数百条无法关联的错误。

## 追踪与上下文传播

入口创建或接受追踪上下文，并在 HTTP、RPC 和消息中传播。Span 应描述真实操作、目标依赖、结果和耗时，不要把高基数值放进会被聚合索引的属性。

固定比例采样简单但可能错过低频错误。可以结合入口采样、错误保留和尾部采样，但任何采样策略都要明确数据丢失边界和成本。

## 控制基数与成本

指标标签的组合数会直接影响内存、存储和查询成本。路径模板应使用 `/orders/{id}`，不能使用包含真实 ID 的 URL。用户、订单和请求标识适合进入日志或追踪，不适合作为指标标签。

为每类遥测数据设置负责人、保留期、采样、脱敏、容量预算和降级策略。观测系统故障时，业务服务不能因为同步写日志或导出遥测而一起阻塞。

## 验证而不是假设

每次发布新服务或新依赖时，主动制造一个成功、超时、拒绝、部分失败和进程重启，确认：

1. 用户 SLI 正确变化。
2. 告警指向受影响服务而不是制造噪声。
3. 日志和追踪可以关联到同一次请求。
4. 看板能区分版本、区域和依赖。
5. 恢复后指标回到基线。

可观测性完成的标准不是“已经接入平台”，而是值班人员能用它在有限时间内证实或排除假设。
