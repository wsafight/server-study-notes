description: 对比令牌桶、漏桶和滑动窗口，并设计分布式配额、拒绝响应和恢复策略。

限流的目标是在系统进入不可恢复的排队和资源耗尽前限制新工作。它既保护服务自身，也保护数据库、第三方接口和不同租户之间的公平性。

## 选择限制维度

先明确限制对象和资源：

- 每个账号、租户、IP、API Key 或接口。
- 并发请求数、每秒请求数、请求字节或计算成本。
- 全局配额、区域配额和单实例局部保护。
- 在线请求与批处理分别使用的容量预算。

只按请求数计费可能让一个昂贵报表查询等同于一次轻量读取。可以根据已验证的成本为操作设置权重，但模型要保持可解释和可观测。

## 常见算法

| 算法 | 特点 | 适用场景 |
| --- | --- | --- |
| 固定窗口 | 实现简单，窗口边界可能允许双倍突发 | 粗粒度配额 |
| 滑动日志 | 精确保留事件，内存随请求数增长 | 低流量高精度控制 |
| 滑动窗口计数 | 在精度与存储间折中 | 常规 API 限流 |
| 令牌桶 | 允许受控突发，长期速率稳定 | 在线请求常用 |
| 漏桶/排队 | 以稳定速率处理输入 | 能接受排队的后台工作 |

排队不是免费缓冲。队列必须有长度、等待时间和丢弃策略，否则限流只是把过载变成长尾延迟。

## 分布式实现

单实例本地限流速度快，但扩缩容会改变全局额度。集中式存储提供更统一的计数，却引入网络、热点和自身可用性问题。

常见折中是把全局配额分片或按批次租给实例，再用本地并发上限保护单机。此时应明确允许的超发范围，以及控制面不可用时选择 fail-open 还是 fail-closed。

资金、登录防爆破等安全边界通常倾向 fail-closed；公开只读接口可能在限流依赖故障时允许保守的本地额度。

## 正确拒绝请求

HTTP API 通常返回 `429 Too Many Requests`，并在能够给出有效建议时提供 `Retry-After`。响应需要区分租户配额、系统过载和下游限流，避免客户端无限快速重试。

优先拒绝低优先级、可重建或超出公平份额的请求。已经接近完成的工作通常比新请求更值得保留，但具体策略取决于资源和业务价值。

## 限流放在哪里

- 边缘网关阻止明显无效或超配额流量进入内网。
- 服务端基于认证后的业务身份实施准确配额。
- 数据库连接池、线程池和队列提供最后的并发边界。
- 下游调用方依据对方返回的限流信息降低发送速率。

只在最外层限流无法保护内部批任务，只在最内层限流又浪费前置资源。

## 验证和监控

记录允许、拒绝、排队和超时数量，按规则、租户、接口和实例观察，但控制标签基数。压测稳定流量、允许突发、多个热点租户、限流存储故障和恢复过程。

修改限额应有版本和审计。长期大量触发限流可能意味着客户端错误、容量不足或产品配额设计不合理，不能只通过提高阈值消除告警。
