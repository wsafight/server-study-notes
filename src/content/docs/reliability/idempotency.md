---
title: 设计幂等请求与消费
description: 使用幂等键、唯一约束、状态机和事务记录处理重复 HTTP 请求与消息投递。
---

幂等表示同一个逻辑操作执行一次或多次，最终业务效果相同。网络超时无法告诉客户端服务端是否已经提交，因此支付、创建订单和消息消费必须把重复当作正常输入处理。

## 定义逻辑请求

客户端为每次业务操作生成不可重复的幂等键，并在重试时复用。幂等键的作用域应包含租户、操作类型和业务主体，避免不同用户之间碰撞：

```text
tenant:42:create-order:01J6...
```

服务端不能仅依赖客户端键格式证明权限。认证、参数校验和业务归属仍需独立检查。

## 在事务中记录结果

一种关系数据库实现是建立幂等记录表，并对作用域内的键设置唯一约束：

```sql
CREATE TABLE idempotency_record (
  tenant_id bigint NOT NULL,
  operation varchar(64) NOT NULL,
  idempotency_key varchar(128) NOT NULL,
  request_hash char(64) NOT NULL,
  status varchar(16) NOT NULL,
  resource_id bigint,
  response_body json,
  created_at timestamp NOT NULL,
  PRIMARY KEY (tenant_id, operation, idempotency_key)
);
```

在同一数据库事务中创建业务数据并完成幂等记录，避免业务已提交但去重状态丢失。重复请求读取已有结果；如果同一个键对应的规范化请求哈希不同，应拒绝而不是返回旧结果。

## 处理中间状态

请求可能在 `processing` 状态时超时。需要定义：

- 谁可以接管超过租约时间的处理中记录。
- 如何确认外部副作用是否已经发生。
- 失败是可以重新执行、永久失败还是需要人工确认。
- 响应保存多久，以及资源删除后重复请求返回什么。

简单的“Key 存在就成功”会把未完成操作误报为完成。

## 消息消费

大多数消息系统提供至少一次投递，消费者必须接受重复。可以使用消息 ID 或业务事件 ID 建立 Inbox 表，在同一事务中记录已消费事件并更新本地状态。

生产消息时使用 Outbox：业务事务同时写业务表和待发送事件，独立发布器重复发送，消费方依靠幂等处理。这样不需要假设数据库提交与消息发送构成分布式原子事务。

## 外部副作用

调用支付、邮件或第三方 API 时，尽量把同一幂等键传给下游。若下游不支持幂等，只靠本地锁无法处理“下游成功但响应丢失”，需要查询下游结果、对账或补偿流程。

## 存储与过期

幂等记录 TTL 必须覆盖客户端最大重试窗口、消息保留和人工补偿周期。过早删除会让旧请求再次产生副作用；永久保存则增加隐私和容量成本。

测试应覆盖同时重复、超时后重复、进程提交后退出、相同键不同参数、记录过期和下游部分成功。幂等不是一个中间件开关，而是完整业务状态机的属性。
