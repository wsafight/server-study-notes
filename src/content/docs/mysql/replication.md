---
title: MySQL 复制与故障切换
description: 理解 binlog、relay log、GTID、复制延迟和主从切换中的一致性边界。
---

MySQL 复制把来源实例的 binlog 事件传输到副本并重新执行。它常用于高可用、只读扩展、备份和数据分发，但默认异步复制不等于零数据丢失，也不自动完成可靠故障切换。

## 复制链路

一条典型链路包括：

1. 来源实例提交事务并写入 binlog。
2. 副本接收线程拉取事件并写入 relay log。
3. SQL 应用线程按依赖关系重放事务。
4. 副本记录已经接收和执行的位置。

GTID 为每个已提交事务提供全局标识，可以简化定位、跳过已执行事务和切换来源。部署新集群时通常应启用 GTID，并在演练中验证自动定位和回退流程。

## 异步与半同步

- **异步复制：** 来源提交不等待副本确认。延迟低，但来源故障时，尚未传输的事务可能丢失。
- **半同步复制：** 来源等待至少一个副本确认收到事务事件后再返回。它缩小数据丢失窗口，但确认收到不代表副本已经应用，也不能替代仲裁和故障转移。

耐久性还受 `sync_binlog`、`innodb_flush_log_at_trx_commit`、存储系统和具体插件配置影响。必须通过故障注入验证实际 RPO，而不是只依据参数名称推断。

## 复制延迟

单一的“落后秒数”无法解释所有问题。至少区分：

- 来源尚未发送的延迟。
- 副本已经接收但尚未应用的延迟。
- 大事务、DDL 或单个热点行阻塞应用线程。
- 副本磁盘、CPU 或并行复制配置形成的资源瓶颈。

使用目标版本提供的 Performance Schema 复制表和 `SHOW REPLICA STATUS` 交叉检查接收、应用、错误与 GTID 集合。监控应以业务可接受的新鲜度为准，并覆盖复制停止而数值未及时变化的情况。

## 读写一致性

刚在来源提交的数据可能尚未出现在只读副本。常见策略包括：

- 写后一定时间内继续读取来源。
- 传递提交的 GTID，等待目标副本执行到该位置后再读取。
- 对余额、权限等强一致读始终访问来源或一致性服务。
- 明确向用户展示分析报表的数据截止时间。

不要在数据访问层随机分流读请求后，才由业务代码猜测为什么读不到刚写入的数据。

## 故障切换清单

1. 确认原来源是否真正不可写，避免双主写入。
2. 比较候选副本的已执行 GTID、延迟、健康度和数据完整性。
3. 提升新来源并让其他副本重新指向它。
4. 切换连接入口，验证客户端重连、事务失败和缓存刷新。
5. 旧来源恢复后先隔离并重新同步，不能直接恢复写流量。

切换流程必须定期演练。没有围栏、仲裁和客户端重试设计的“自动切换”，可能把短暂不可用扩大为数据分叉。
