---
title: 分库策略与边界
description: 从业务边界和水平扩展理解分库，并评估事务、查询和运维成本。
---

分库通常有两种目的：按业务边界隔离数据，或把同一业务的数据水平分散到多个数据库实例。两种方案解决的问题不同。

## 按业务边界拆分

用户、订单、结算等边界可以拥有独立数据库，由对应服务负责写入。这样可以隔离容量、权限和故障，但要求边界清晰：

- 其他服务通过 API 或事件获取数据，不直接依赖内部表结构。
- 跨服务一致性使用本地事务、Outbox、幂等消费和补偿流程。
- 报表与搜索通过数据同步构建读模型，不在在线请求中跨库大 JOIN。

不要按“日志库、统计库、图片库”等固定模板机械拆分。对象存储、日志平台、数仓和关系数据库各自适合不同数据，应该按访问模式选择系统。

## 水平分库

当单实例容量或写入吞吐成为明确瓶颈时，可以按租户、用户或订单等分片键把相同表结构分布到多个实例。它与水平分表面临相同的路由、扩容和倾斜问题，但故障域和运维成本更大。

## 关键成本

- 跨库事务不再由一个 InnoDB 事务自然保证。
- 全局唯一键、外键约束和跨库排序/分页需要重新设计。
- Schema 变更、备份、恢复和故障演练要覆盖全部实例。
- 应用连接池总量会随实例数增长，必须控制每个进程的连接预算。
- 按城市或地区建库只有在数据驻留、延迟或独立容量确有需求时才合理。

实施分库前应证明单库优化、读写分离、归档和垂直扩容无法满足 SLO，并准备完整的数据迁移、校验和回滚路径。
