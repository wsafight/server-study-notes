备份的目标不是生成文件，而是在规定时间内恢复到可接受的数据时间点。只有成功完成过恢复演练、校验结果且记录耗时的备份，才可以被视为有效。

## 先定义恢复目标

- **RPO：** 最多允许丢失多长时间的数据，例如 5 分钟。
- **RTO：** 从故障发生到服务恢复最多允许多长时间，例如 30 分钟。
- **恢复粒度：** 整个实例、单库、单表，还是误删前的某个时间点。
- **故障范围：** 磁盘损坏、误操作、区域故障、凭据泄露或逻辑污染。

不同目标会决定备份频率、binlog 保留期、异地副本和恢复基础设施成本。

## 选择备份方式

| 方式 | 优点 | 主要限制 |
| --- | --- | --- |
| 逻辑备份 | 可读、可筛选对象、跨版本迁移较灵活 | 大库导出和导入通常较慢，恢复时需要重建索引 |
| 物理备份 | 大数据量下备份和恢复通常更快 | 与版本、平台和工具兼容性关系更紧密 |
| 存储快照 | 创建快，适合整卷恢复 | 必须保证数据库一致性，并处理跨卷顺序和 binlog 位置 |

可使用 `mysqldump` 或 MySQL Shell 执行逻辑备份，使用 MySQL Enterprise Backup、Percona XtraBackup 或云平台能力执行物理备份。选择工具时应基于目标版本、授权、加密和恢复验证，而不是只比较备份速度。

## 按时间点恢复

PITR 通常由一个一致的全量备份，加上该备份之后连续保留的 binlog 组成：

1. 恢复全量备份到隔离实例。
2. 找到备份对应的 binlog 文件、位置或 GTID 集合。
3. 使用 `mysqlbinlog` 重放后续事件，在误操作前的时间或事务边界停止。
4. 校验关键表、约束、业务汇总和应用读写。
5. 通过受控切流恢复服务。

binlog 缺失任何一段都可能使时间点恢复链断裂。具体解析方法参见[使用 mysqlbinlog 分析二进制日志](../binlog/)。

## 备份安全

- 备份文件与生产实例使用不同故障域和权限边界。
- 传输和静态存储都启用加密，并定期测试密钥可用性。
- 防止生产账号直接删除所有历史备份，保留不可变或延迟删除副本。
- 对备份中的个人信息、密钥和审计数据执行与生产相同的访问控制。
- 同时备份用户、权限、事件、例程和必要配置，避免只保存业务表。

## 恢复演练清单

至少定期自动恢复到一套隔离环境，记录下载、解密、恢复、重放和校验各阶段耗时。演练应随机选择历史恢复点，并验证行数、关键聚合、外键或业务一致性，而不只是确认 MySQL 能启动。

当数据规模、版本、加密方式或拓扑变化后，重新测量 RTO。恢复手册还应包含负责人、所需权限、流量切换和失败回退步骤，确保事故发生时不依赖个人记忆。
