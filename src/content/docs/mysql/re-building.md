---
title: 重建 InnoDB 表
description: 判断何时需要重建表，并控制磁盘空间、元数据锁、在线 DDL 和复制风险。
---

InnoDB 删除记录后，空闲页通常留在表空间中供后续写入复用。对于启用 `innodb_file_per_table` 的独立表空间，删除大量数据也不一定让 `.ibd` 文件立即缩小。

## 什么时候考虑重建

- 一次性删除了大量数据，并且确实需要把空间归还文件系统。
- 主键更新或随机写入造成的碎片已经产生可测量的扫描或缓存成本。
- 需要同时变更行格式、压缩或其他必须重建的表属性。

如果表很快会重新写入相同规模的数据，保留可复用空间通常比重建更经济。`DATA_FREE` 是近似统计值，不能单独证明查询变慢。

## 常见命令

对 InnoDB，`OPTIMIZE TABLE` 通常通过重建表和索引来整理空间：

```sql
OPTIMIZE TABLE events;
```

也可以显式请求重建：

```sql
ALTER TABLE events ENGINE = InnoDB;
```

具体使用 `INSTANT`、`INPLACE` 还是 `COPY`，以及是否支持 `LOCK=NONE`，取决于 MySQL 版本和变更类型。可以显式指定期望算法让不支持时立即失败，但不能假设所有重建都完全在线。

## 风险清单

- 新表、临时文件、binlog 和在线变更日志需要额外磁盘空间。
- Online DDL 仍会在开始和结束阶段获取元数据锁，长事务可能让它等待。
- 高并发 DML 会增加重放日志，延长完成时间并影响尾延迟。
- 重建产生大量 I/O 和复制流量，可能造成副本延迟或备份窗口冲突。
- 失败后的清理与回滚也需要空间和时间。

大表应先在同等规模环境估算时间与空间，设置变更窗口、监控和停止条件。无法接受原生 DDL 影响时，可以评估 `gh-ost` 或 `pt-online-schema-change`，但这些工具同样需要主键、复制、触发器和故障恢复方面的演练。
