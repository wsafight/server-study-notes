---
title: 安全执行 MySQL 在线 DDL
description: 理解 INSTANT、INPLACE、COPY 算法和元数据锁，并为大表结构变更设计灰度与回滚。
---

“在线 DDL”只表示操作允许一定程度的并发读写，不代表没有锁、没有资源消耗或没有复制影响。表结构变更前必须确认目标 MySQL 版本、具体操作、表特征和可用磁盘空间。

## 三类执行算法

- **`INSTANT`：** 主要修改数据字典，通常不扫描或重写所有行，但只支持特定操作。
- **`INPLACE`：** 避免传统的完整表复制，某些操作仍会重建表并消耗大量 I/O、CPU 和临时空间。
- **`COPY`：** 创建新表并复制数据，成本最高，通常会限制并发写入。

支持范围随版本、数据类型和操作组合变化。可以显式要求算法，让不满足条件的变更失败，而不是静默退化为更重的执行方式：

```sql
ALTER TABLE orders
  ADD COLUMN source varchar(32) NULL,
  ALGORITHM=INSTANT;
```

MySQL 没有可替代真实执行的通用 DDL 预演命令。先根据目标版本文档确认支持范围，显式指定期望算法让不兼容操作快速失败，再在同版本、相近数据量的环境实测。

## 元数据锁仍然存在

DDL 开始和结束阶段需要元数据锁。一个长期未提交、曾访问目标表的事务，就可能让 DDL 等待；后续查询又排在 DDL 后面，最终形成请求堆积。

变更前检查长事务和当前元数据锁：

```sql
SELECT *
FROM information_schema.innodb_trx
ORDER BY trx_started;

SELECT *
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'app' AND OBJECT_NAME = 'orders';
```

为锁等待设置保守上限，使无法快速获得元数据锁的变更尽早失败。不要在业务高峰无限等待。

## 评估资源和复制影响

- 预留表与索引重建、临时文件、binlog 和备份所需空间。
- 观察磁盘吞吐与延迟、Buffer Pool 命中、CPU、redo 生成和历史版本增长。
- 大事务或重建事件可能让副本明显落后，切换窗口内尤其危险。
- 新索引会增加后续写放大和 Buffer Pool 占用，不能只验证创建过程。
- 对分区、外键、全文索引和生成列单独验证工具支持边界。

## 原生 DDL 与外部工具

当原生算法无法满足锁定时间目标时，可以评估 `gh-ost` 或 `pt-online-schema-change`。这类工具通常创建影子表、增量同步并最终换表，会引入额外磁盘、binlog、触发器或复制拓扑要求。

工具不会消除最终换表所需的元数据锁，也可能与外键、触发器、级联操作和故障切换冲突。必须先在真实拓扑演练暂停、恢复、取消和失败清理。

## 上线步骤

1. 保存原始 Schema，确认兼容发布顺序和回滚方式。
2. 在副本或相近环境测量耗时、空间和负载。
3. 设置终止条件，选择低峰窗口并暂停冲突批任务。
4. 小步执行，持续监控主库、连接池和所有副本。
5. 验证新旧应用版本、查询计划和数据一致性。

删除列、缩短类型等破坏性变更应采用“先停止读取、再停止写入、最后清理”的多阶段发布。很多 DDL 无法低成本逆转，回滚方案通常是向前修复或从备份恢复。
