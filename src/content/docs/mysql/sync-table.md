---
title: 数据库迁移与安全切流
description: 使用全量复制、CDC、校验、停写窗口和可回滚路由完成数据库迁移。
---

数据库迁移通常分为 Schema 准备、全量复制、增量 CDC、数据校验和业务切流。真正困难的不是把历史数据复制过去，而是在持续写入时确定唯一写入源并保证切换可回滚。

## 标准阶段

1. **兼容性检查：** 核对版本、字符集、排序规则、时区、账号、表结构和不支持的对象。
2. **全量复制：** 记录一致性快照位置，并把已有数据导入目标库。
3. **增量同步：** 从快照对应的 binlog position 或 GTID 开始持续应用变更。
4. **数据校验：** 比较行数、分段校验和、关键业务聚合与抽样记录。
5. **切流：** 控制旧实例写入，等待 CDC 追平，再原子切换连接或路由。
6. **观察与回滚窗口：** 保留源库和回切路径，确认目标稳定后再结束迁移。

## 避免双写冲突

在单向 CDC 同步源库到目标库时，不要同时让业务直接写目标库的同一批表。自增 ID、唯一键、更新顺序和删除都可能冲突。简单跳过一段 ID 或临时改成 `(id, operator_id)` 复合主键，不能解决更新覆盖和业务一致性问题。

常见安全方案：

- 在短暂停写窗口内切换，流程最容易验证。
- 通过统一写入代理或 Feature Flag 确保任意时刻只有一个主写端。
- 必须双写时使用稳定业务 ID、Outbox 和幂等消费，并定义部分失败后的补偿与对账。
- 双向 CDC 只适合已经设计好冲突检测、全局 ID 和循环复制过滤的系统。

## 多实例应用切流

- 先让新版本同时兼容源库与目标库 Schema。
- 通过集中配置或路由逐步切读，验证结果后再切写。
- 切写前停止或排空仍会写源库的旧 Pod、任务和消费者。
- 观察 CDC 延迟归零，并再次校验最后增量。
- 回滚时明确新产生的数据如何同步回源库，不能只把连接字符串改回去。

迁移窗口应根据流量和风险选择，不等于固定在深夜。低流量可以降低影响，但值班、监控和依赖方必须同时具备处理故障的能力。
