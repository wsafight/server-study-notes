连接池复用已经建立的 MySQL 会话，减少认证与握手成本，并限制进入数据库的并发。池越大不代表吞吐越高；超过 CPU、I/O 和锁的可并行能力后，更多连接通常只增加排队和内存。

## 从容量而不是实例数计算

数据库连接预算应覆盖所有应用实例、后台任务、迁移工具、管理和故障冗余：

```text
总连接上限 >= 在线实例数 × 单实例池上限 + 运维预留
```

滚动发布或故障转移期间，新旧实例可能同时存在。自动扩容也会让固定单实例池迅速超过数据库 `max_connections`。

使用负载测试逐步增加活跃连接，观察吞吐、P95/P99、CPU、磁盘、行锁、Buffer Pool 和队列。当吞吐不再增长或尾延迟快速上升时，继续加连接没有价值。

## 设置有界等待

连接池至少区分：

- 最大连接数和最小空闲连接数。
- 获取连接的等待超时。
- 空闲连接超时和最大生命周期。
- 连接建立与认证超时。
- SQL、锁等待和整个请求截止时间。

池满时应在应用侧短暂排队或快速拒绝，队列必须有长度和时间上限。无限等待会占满请求线程，并把数据库过载扩散到整个服务。

获取连接的超时要短于入口剩余截止时间；否则即使最终拿到连接，用户请求也可能已经取消。

## 正确归还连接

连接是带状态的会话。归还前必须结束事务，并按照驱动或池的能力清理：

- 隔离级别、只读状态和自动提交。
- 会话变量、SQL mode、字符集和时区。
- 临时表、用户变量、命名锁和服务端预处理语句。
- 未读取完的结果集与警告。

不要在业务代码异常后直接把仍处于事务中的连接放回池。池应验证连接状态，必要时丢弃并重建。

## 处理长事务与泄漏

使用结构化资源管理保证每条路径都关闭连接。监控池中 active、idle、pending、获取耗时和超时，并把借出连接与请求追踪关联。

连接池只能限制会话数，不能防止一个事务持锁很久。数据库侧同时监控当前事务、锁等待和语句耗时，参见[事务与隔离级别](../transaction-isolation/)和[死锁诊断](../deadlock/)。

## 故障切换与凭据轮换

已有连接可能长期指向旧主库，也可能在网络设备中成为半开连接。使用最大生命周期逐步更新连接，并在操作失败时识别失效连接；不能对未确认结果的写操作盲目重试。

故障切换后，连接池应重新解析地址或刷新服务发现、丢弃旧连接，并等待新主库真正可写。凭据与证书轮换同样需要新旧配置重叠窗口和分批重连，避免同时断开所有会话。

## 验证场景

压测正常峰值、数据库变慢、池耗尽、应用扩容、主库切换和凭据轮换。确认请求在明确上限内失败，恢复时连接不会同时重建冲击数据库，且没有事务或会话状态泄漏到下一个请求。
