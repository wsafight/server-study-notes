存储引擎不仅要完成 `read(key)` 和 `write(key, value)`，还要支持范围扫描、并发、崩溃恢复，并尽量减少昂贵的随机 I/O。数据结构的选择是这些目标之间的权衡。

## 先明确基本操作

- **点查：** 根据一个键找到记录。
- **范围扫描：** 按键顺序读取 `[begin, end)` 内的记录。
- **写入：** 插入、更新和删除，同时维持结构。
- **持久化：** 让结构适合按页读写、日志恢复和并发控制。

## 其他数据结构的取舍

### 哈希表

哈希表点查平均接近 `O(1)`，但键没有顺序，范围扫描需要遍历大量桶。它适合等值访问，不适合作为通用有序索引。

### 有序数组

紧凑有序数组具有很好的空间局部性，点查为 `O(log N)`，范围扫描为 `O(log N + K)`。但在中间插入通常要移动大量元素，持续更新成本高。

### 平衡二叉搜索树

点查和更新为 `O(log N)`，也能按序遍历。但每个节点只有少量子节点，数据放在磁盘时树高较大；指针跳转还会降低页和 CPU Cache 的局部性。

## B+ 树的优势

B+ 树让一个内部节点保存大量分隔键和子页指针，因此扇出很高、树高很低。内部节点只负责导航，完整记录位于叶子层；叶子页按键排列并相互连接，范围扫描可以连续读取。

这带来几个结果：

- 点查只需访问少量树层。
- 范围查询定位起点后可以顺序扫描叶子页。
- 固定大小页面便于 Buffer Pool、预读、锁和恢复机制管理。
- 页分裂、合并和重分布让更新成本保持在可控范围。

## 为什么不是唯一选择

LSM Tree 通过顺序写和后台合并换取更高写入吞吐，哈希索引适合纯等值场景，列式存储更适合分析扫描。InnoDB 选择 B+ 树，是因为它需要同时支持事务型工作负载中的点查、范围查询和持续更新。

理解索引结构后，更重要的是根据查询模式设计键顺序，并用真实执行计划验证，而不是只记住“B+ 树层数少”。
