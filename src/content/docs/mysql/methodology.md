---
title: SQL 性能优化方法论
description: 从定义问题、收集证据、定位成本到灰度验证建立可重复的 SQL 优化流程。
---

SQL 优化不是看到全表扫描就加索引，也不是把语句改得更短。目标是在保证结果正确的前提下，用可验证的方式降低响应时间、资源消耗或锁影响。

## 1. 定义问题

先明确可量化的现象：

- 哪个接口、任务或报表变慢。
- P50、P95、P99 延迟和错误率如何变化。
- 问题是持续发生、周期发生还是最近版本引入。
- 影响单条 SQL、一个实例还是整个依赖链。

没有基线和目标，就无法判断优化是否成功。

## 2. 收集真实证据

- 从链路追踪、慢查询日志或 `performance_schema` 获取 SQL、耗时和执行次数。
- 保存真实参数范围，但对敏感数据脱敏。
- 同时观察 CPU、磁盘、Buffer Pool、连接池、锁等待和复制延迟。
- 对照代码、Schema、统计信息和最近发布变更。

高频的 5 ms 查询也可能比偶发的 2 s 查询消耗更多总资源，应同时看单次延迟和累计时间。

## 3. 定位执行成本

先用 `EXPLAIN` 查看计划，再在安全环境使用 `EXPLAIN ANALYZE` 对比实际行数与估算：

- 读取了多少行，最终返回多少行。
- 哪个节点循环次数最多。
- 是否发生大规模回表、排序、临时表或重复子查询。
- 连接顺序和索引是否符合数据分布。
- 是否因锁等待而慢，而不是 SQL 计算本身慢。

## 4. 从减少工作量入手

通常按风险从低到高评估：

1. 缩小查询范围，只返回需要的行和列。
2. 修正隐式转换、函数条件和不稳定分页。
3. 设计或调整索引，减少扫描、回表和排序。
4. 改写重复访问、相关子查询或不必要的聚合。
5. 根据真实业务需求减少不需要的计算或一致性强度。
6. 最后才考虑分库分表、缓存或引入新存储系统。

“不改 SQL”与“必须改 SQL”都不是原则。应该选择能够解决已定位成本、风险最小且可长期维护的方案。

## 5. 验证正确性与收益

- 使用代表性数据和参数比较变更前后的结果集。
- 压测吞吐、尾延迟、CPU、I/O、锁和写入放大。
- 新索引或 DDL 需要评估构建时间、磁盘空间、元数据锁和复制延迟。
- 检查优化是否让其他查询退化。

## 6. 灰度与回滚

在小流量或单个实例上灰度，保留旧查询或索引的回滚路径。上线后观察完整业务周期，不要只用一次手工执行时间宣布成功。

最后记录问题、证据、决策、结果和适用版本，让一次优化转化为团队可复用的方法。
