---
title: 分表策略与边界
description: 对比水平分表、垂直拆分和 MySQL 分区表，并说明分片带来的系统复杂度。
---

分表是把一张逻辑表的数据拆到多个物理表。它会降低单表容量或热点，但同时引入路由、跨表查询、全局唯一性、迁移和运维复杂度，应在索引、SQL、归档和实例扩容无法满足目标后再采用。

## 水平分表

水平分表保持列结构一致，按行拆分。

- **哈希分片：** `hash(user_id) % n` 分布通常较均匀，单用户查询容易路由，但扩容和范围查询成本较高。
- **范围分片：** 按日期或 ID 范围拆分，归档和范围扫描方便，但最新分片可能成为热点。
- **路由表：** 显式保存业务主体到分片的映射，迁移灵活，但需要高可用的路由数据。

分片键应尽量出现在核心查询中。缺少分片键的请求会广播到多个表，分页、排序和聚合都需要在应用或中间件中合并。

## 垂直拆分

垂直拆分把访问频率和生命周期不同的列放到一对一或一对多附表。例如把很少读取的大文本从订单主表拆到 `order_details`。这样可以降低热点行宽，但会增加查询和一致性维护成本。

不要仅因为字段是 `TEXT`/`BLOB` 就机械拆表。InnoDB 支持溢出页，是否拆分仍要依据查询模式、缓存命中和更新频率。

## 分区表不是分表中间件

MySQL 分区表仍属于同一逻辑表和实例，优化器可以做分区裁剪，删除旧分区也很高效。但它不会突破单实例 CPU、内存和写入能力，也不能自动提供跨实例扩展。

## 实施前检查

- 路由规则是否支持扩容、回滚和历史数据迁移。
- 唯一键、外键、事务和 ID 如何跨分片处理。
- DDL、备份、恢复和数据校验能否覆盖所有分片。
- 跨分片查询是否有明确的超时、并发和结果上限。
- 每个分片是否具备独立容量与热点监控。

先定义可量化的瓶颈和目标，再决定是否分表以及采用哪种策略。
