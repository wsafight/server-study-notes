description: 从死锁日志、锁等待和访问顺序定位循环依赖，并设计可重试的事务。
---

当多个事务各自持有对方需要的锁，形成循环等待时就会发生死锁。InnoDB 通常会检测循环并回滚其中一个事务，让其他事务继续执行。死锁是并发控制的一部分，不等同于数据库损坏。

## 一个典型场景

两个事务以相反顺序更新两行：

```sql
-- 事务 A
UPDATE account SET balance = balance - 10 WHERE id = 1;
UPDATE account SET balance = balance + 10 WHERE id = 2;

-- 事务 B
UPDATE account SET balance = balance - 20 WHERE id = 2;
UPDATE account SET balance = balance + 20 WHERE id = 1;
```

如果两边同时完成第一条语句，就可能互相等待第二行。实际系统中的循环还可能涉及二级索引、外键检查、间隙锁和唯一键冲突。

## 收集证据

最近一次被检测到的死锁可以通过下面的命令查看：

```sql
SHOW ENGINE INNODB STATUS;
```

重点记录每个事务正在执行的 SQL、已持有和等待的锁、使用的索引以及被回滚的事务。持续诊断时，可以临时评估 `innodb_print_all_deadlocks`，让所有死锁进入错误日志；开启前要考虑日志量和敏感 SQL 脱敏。

当前锁等待可从 Performance Schema 观察：

```sql
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.data_locks;
```

死锁结束后相关等待已经消失，因此必须保留错误日志、事务上下文和链路标识。

## 降低发生概率

1. 所有代码路径按相同顺序锁定资源，例如始终按主键升序更新账户。
2. 为过滤条件建立正确索引，避免扫描并锁住远多于目标的数据。
3. 缩短事务，不在持锁期间执行 RPC、文件 I/O 或人工交互。
4. 将超大批次拆分，但同时检查拆分后业务原子性是否仍成立。
5. 使用唯一约束或单条条件更新替代“先查再写”的竞态流程。

## 正确重试

应用收到死锁错误后，当前事务已经失败。必须回滚并从事务入口重新执行全部业务逻辑：

- 设置有限次数并使用带抖动的退避，避免并发请求立即再次碰撞。
- 只重试幂等操作，或使用业务请求号保证重复执行不会产生重复副作用。
- 把数据库事务之外的消息发送、支付调用等副作用纳入 Outbox 或补偿设计。
- 记录最终失败，不能无限重试掩盖持续的锁设计问题。

关闭死锁检测通常不是解决方案。它会把快速失败变成长时间锁等待，只适合经过压测和架构评估的极特殊热点负载。
