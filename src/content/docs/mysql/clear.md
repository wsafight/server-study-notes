---
title: 安全清理过期数据
description: 通过保留策略、索引、分批删除和分区管理控制大表清理的锁、日志与复制影响。
---

过期数据清理不仅是执行一条 `DELETE`。大事务会产生大量 undo、redo 和 binlog，延长锁持有时间，并可能造成复制延迟。开始前应先明确保留周期、归档要求和可恢复方案。

## 为保留条件建立索引

按创建时间清理时，可以使用 `(created_at, id)` 索引稳定定位旧数据：

```sql
CREATE INDEX idx_events_created_id
ON events (created_at, id);
```

索引本身也有构建成本，大表应先评估 Online DDL、磁盘空间和元数据锁。

## 分批删除

```sql
DELETE FROM events
WHERE created_at < '2026-05-01 00:00:00'
ORDER BY created_at, id
LIMIT 5000;
```

循环执行直到影响行数为 0，每批独立提交，并根据线上延迟、复制延迟和磁盘负载动态休眠或停止。截止时间应在任务开始时固定，避免长任务中边界持续变化。

如果 `created_at` 没有索引，按自增 ID 扫描并假设 ID 与时间严格相关并不安全。优先补索引，或在离线环境生成待删除主键集合后分批执行。

## 归档与分区

有合规或审计要求时，先把数据写入归档存储，校验行数和校验和后再删除。归档和删除跨系统时通常不是同一个事务，需要设计幂等与重试。

按时间保留的大表可以在建表阶段评估分区。删除完整旧分区只涉及元数据，通常比逐行删除高效：

```sql
ALTER TABLE events DROP PARTITION p202605;
```

分区边界必须与保留策略完全一致，且删除分区同样不可依赖事务回滚。

## 是否需要回收空间

InnoDB 删除后释放的页通常可以被同一表复用，但 `.ibd` 文件不一定缩小。只有确实需要归还文件系统空间或碎片已造成可测量影响时，才评估重建表。

`information_schema.tables.DATA_FREE` 只是近似信息，不能单独作为重建依据。重建会消耗额外磁盘、I/O 和复制资源，具体流程参见[重建 InnoDB 表](../re-building/)。
