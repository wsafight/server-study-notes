---
title: 规划自增主键容量
description: 对比 MySQL 整数类型范围，并从增长速度、存储和客户端兼容性选择主键类型。
---

自增主键的数据类型决定可分配 ID 的上限。`UNSIGNED` 不改变字段占用字节数，但把负数范围用于更大的正整数空间。

| 类型 | 字节 | 有符号最大值 | 无符号最大值 |
| --- | ---: | ---: | ---: |
| `TINYINT` | 1 | 127 | 255 |
| `SMALLINT` | 2 | 32767 | 65535 |
| `MEDIUMINT` | 3 | 8388607 | 16777215 |
| `INT` | 4 | 2147483647 | 4294967295 |
| `BIGINT` | 8 | 9223372036854775807 | 18446744073709551615 |

## 选择原则

- 根据峰值写入速度和保留周期估算至少数年的增长空间。
- 数据量可能超过 21 亿时，不要使用有符号 `INT` 作为长期主键。
- 主键会被复制到每个 InnoDB 二级索引中，类型越宽，所有二级索引也越大。
- 外键列必须使用兼容的数据类型和符号属性。
- JavaScript `number` 无法精确表示所有 64 位整数，API 中可能需要使用字符串或 `bigint`。

MySQL 8.0.17 起已弃用整数显示宽度。`INT(11)` 中的 `11` 不限制数值范围，也不会改变存储空间，不应再用它表达业务长度。

主键设计完成后仍要监控 `AUTO_INCREMENT` 当前值和增长速度，避免到接近上限时才进行大表类型变更。
