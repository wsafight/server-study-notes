---
title: 规划自增主键容量
description: 对比 MySQL 整数类型范围，并从增长速度、存储和客户端兼容性选择主键类型。
---

自增主键的数据类型决定可分配 ID 的上限。`UNSIGNED` 不改变字段占用字节数，但把负数范围用于更大的正整数空间。

| 类型 | 字节 | 有符号最大值 | 无符号最大值 |
| --- | ---: | ---: | ---: |
| `TINYINT` | 1 | 127 | 255 |
| `SMALLINT` | 2 | 32767 | 65535 |
| `MEDIUMINT` | 3 | 8388607 | 16777215 |
| `INT` | 4 | 2147483647 | 4294967295 |
| `BIGINT` | 8 | 9223372036854775807 | 18446744073709551615 |

## 选择原则

- 根据峰值写入速度和保留周期估算至少数年的增长空间。
- 数据量可能超过 21 亿时，不要使用有符号 `INT` 作为长期主键。
- 主键会被复制到每个 InnoDB 二级索引中，类型越宽，所有二级索引也越大。
- 外键列必须使用兼容的数据类型和符号属性。
- JavaScript `number` 无法精确表示所有 64 位整数，API 中可能需要使用字符串或 `bigint`。

MySQL 8.0.17 起已弃用整数显示宽度。`INT(11)` 中的 `11` 不限制数值范围，也不会改变存储空间，不应再用它表达业务长度。

## 估算耗尽时间

容量不能只看当前行数。批量预分配、失败插入、回滚和删除都会消耗或留下自增值空洞。使用最近一段时间的 `AUTO_INCREMENT` 增长速度估算，而不是用 `COUNT(*)` 代替当前值。

```sql
SELECT
  table_schema,
  table_name,
  auto_increment
FROM information_schema.tables
WHERE table_schema = 'app'
  AND auto_increment IS NOT NULL
ORDER BY auto_increment DESC;
```

将当前值除以类型上限得到使用比例，再根据峰值而非平均增长速度估算剩余时间。告警阈值要预留大表变更、外键调整、灰度发布和回滚所需周期。

## 连续性不是承诺

自增主键保证生成方向和会话内返回机制，不保证没有空洞，也不代表提交时间或业务发生顺序。事务回滚、批量插入和不同 `innodb_autoinc_lock_mode` 都可能让值不连续。

需要审计连续编号时，应建立独立业务流程和严格的并发、作废规则，不能直接复用表主键。

## 扩容与迁移

把 `INT` 改为 `BIGINT` 可能重建大表，并要求所有外键列、应用模型、序列化协议和下游仓库同步兼容。迁移前应检查：

- 所有引用列的类型和 `UNSIGNED` 属性。
- 二级索引增长和额外磁盘空间。
- Online DDL 的算法、锁、WAL/Binlog 与复制延迟。
- ORM、驱动和 JavaScript 客户端对 64 位整数的表示。
- 回滚期间新旧应用能否同时处理扩大后的值。

主键设计完成后仍要监控当前值、增长速度和预计耗尽日期。接近上限时再做大表类型变更，通常已经没有足够安全窗口。
