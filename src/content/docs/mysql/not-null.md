title: 正确设计 NULL 与 NOT NULL
description: 根据业务语义选择可空列，并理解 NULL 对比较、聚合、约束和索引的影响。
---

列是否允许 `NULL` 首先是数据语义问题。能够保证必填的属性应使用 `NOT NULL`，未知、不适用或尚未发生的值可以使用 `NULL`。不要仅为微小的存储或性能差异把所有列强制设为 `NOT NULL`。

## NULL 的语义

`NULL` 表示未知或缺失，不等于 `0`、空字符串或某个特殊日期：

```sql
-- 正确判断 NULL
WHERE paid_at IS NULL

-- 不能写成 paid_at = NULL
```

包含 `NULL` 的普通比较结果为 unknown，会影响 `WHERE`、`JOIN` 和约束判断。聚合函数通常忽略 `NULL`，但 `COUNT(*)` 仍统计整行。

## 索引与唯一约束

InnoDB 会在 B+ 树索引中保存 `NULL`。MySQL 唯一索引通常允许出现多个 `NULL`，因为它们不被视为彼此相等。如果业务要求“最多一条未填写值”，需要额外设计约束或生成列。

## 设计建议

- 新表按领域含义选择可空性，并提供真正合理的默认值。
- 不要用 `1970-01-01`、`-1` 等哨兵值代替未知，除非领域明确赋予它含义。
- 把可空列改为 `NOT NULL` 前，先清理历史数据并检查所有写入路径。
- 查询中明确处理三值逻辑，必要时使用 `COALESCE`，但不要掩盖数据质量问题。

`NOT NULL` 可以让约束和代码契约更清晰；性能收益通常只是次要因素。
