一次 API 请求通常经过名称解析、连接建立、TLS 握手、HTTP 交换、反向代理和应用处理。只看到“连接超时”或“502”时，需要先判断失败发生在哪一层。

## 推荐顺序

1. [TCP 连接与故障诊断](./tcp/)：理解握手、重传、流量控制、拥塞控制和连接关闭。
2. [DNS 解析与变更](./dns/)：理解递归查询、缓存、TTL 和服务切换的传播边界。
3. [HTTP 请求语义](./http/)：掌握方法、状态码、缓存、连接复用和版本差异。
4. [TLS 证书与握手](./tls/)：诊断证书链、主机名、SNI、ALPN 和双向认证。
5. [反向代理与负载均衡](./reverse-proxy/)：设计转发头、超时、重试、健康检查和连接池。

## 按现象选择入口

| 现象 | 优先检查 |
| --- | --- |
| 域名偶发解析失败 | DNS 返回码、解析链、缓存与目标记录 |
| 连接建立慢 | TCP SYN 重传、路由、防火墙和监听队列 |
| 证书错误 | 系统时间、主机名、证书链、SNI 和信任库 |
| 502/504 | 代理日志、上游连接、请求截止时间和应用状态 |
| 单个大请求慢 | 请求/响应字节、代理缓冲、流控和应用处理 |
| 发布时连接重置 | readiness、连接排空、客户端重试与幂等 |

主机侧指标和命令参见 [Linux 网络问题排查](../linux/network/)，调用链超时策略参见[超时、重试与退避](../reliability/timeout-retry/)。

## 实验建议

准备客户端、代理和服务端三个可控制节点，分别模拟 DNS 返回旧地址、SYN 丢包、证书过期、上游慢响应、代理超时和服务停机。将客户端分阶段计时、代理日志、服务追踪和抓包对齐到同一时间线。

抓包和详细请求日志可能包含 Cookie、Token、查询参数和业务正文。生产采集前必须限制过滤条件、文件大小、访问权限和保留时间。
