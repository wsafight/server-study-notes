DNS 把名称映射为地址和其他服务信息。一次应用解析可能经过进程缓存、操作系统 Stub Resolver、本地缓存、递归解析器和权威服务器，每一层都可能保留不同时间的结果。

## 一次解析过程

客户端向递归解析器请求记录；如果没有缓存，递归解析器从根、顶级域和权威服务器逐级查询，最后把结果与 TTL 返回。常用记录包括：

- `A`、`AAAA`：IPv4 和 IPv6 地址。
- `CNAME`：将一个名称指向另一个规范名称。
- `MX`：邮件交换服务器。
- `TXT`：验证、安全策略和其他文本信息。
- `SRV`：服务的目标、端口、优先级和权重。

CNAME 链过长会增加查询和故障面；根域、CNAME 与其他记录的组合也受 DNS 规则和供应商实现限制。

## TTL 不是精确切换计时器

TTL 表示缓存结果最多可复用的时间，但实际生效还受以下因素影响：

- 记录修改前已经缓存的旧 TTL。
- 操作系统、JVM、浏览器或应用自定义缓存策略。
- 递归解析器对最小和最大 TTL 的限制。
- 长连接继续使用旧地址，不会因为 DNS 变化自动迁移。
- 负缓存保留 `NXDOMAIN` 或无记录响应。

因此不能承诺“TTL 到期后所有流量立即切换”。

## 诊断命令

```bash
dig api.example.com A
dig api.example.com AAAA
dig @1.1.1.1 api.example.com A
dig +trace api.example.com
```

比较不同递归解析器的返回码、Answer、权威信息、TTL 和查询时间。`+trace` 直接遍历委派链，路径与普通客户端使用的递归解析器不同，适合诊断权威和委派，不代表真实用户延迟。

间歇性故障要记录当时查询的服务器、返回码和完整响应。只在故障结束后执行一次 `dig` 很可能看不到问题。

## 安全变更流程

1. 提前将 TTL 降到计划值，并等待旧 TTL 的完整周期。
2. 先确保新旧地址都能安全承载流量。
3. 修改记录后从多个网络和解析器验证。
4. 保留旧目标直到缓存和长连接窗口结束。
5. 观察请求量、错误、证书和数据一致性，再恢复正常 TTL。

DNS 轮询不是健康检查。递归缓存可能继续返回故障地址，需要代理、客户端或服务发现层提供真正的失败检测。

## 安全边界

- 域名托管账号启用强认证、最小权限和变更审计。
- 使用 DNSSEC 时要同时维护签名、DS 和密钥轮换，配置错误可能让整个域无法验证。
- 服务端抓取用户提供的 URL 时防范 DNS Rebinding：解析后校验目标地址，并在连接阶段防止跳转到内网或元数据地址。
- 不要在日志中无条件记录包含凭据或个人信息的完整查询名称。

应用应对解析失败设置短而有界的重试，并区分不存在、暂时失败和超时。无限缓存与完全不缓存都会制造不同的可靠性问题。
