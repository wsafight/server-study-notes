HTTP 是请求与响应协议。可靠的 API 不只需要能够传输 JSON，还要正确表达方法语义、失败类型、缓存边界、消息大小和连接生命周期。

## 方法与幂等性

- `GET`、`HEAD` 用于读取，不应产生用户可见副作用。
- `POST` 通常创建资源或执行命令，默认不幂等。
- `PUT` 表示创建或替换目标资源，按定义应幂等。
- `PATCH` 执行部分修改，是否幂等取决于补丁语义。
- `DELETE` 的目标效果应幂等，多次调用的响应状态可以不同。

协议定义不会自动约束应用实现。带副作用的重试仍需[幂等键和持久状态](../../reliability/idempotency/)。

## 使用准确状态码

| 范围 | 含义 | 示例 |
| --- | --- | --- |
| 2xx | 请求成功处理 | `200`、`201`、`204` |
| 3xx | 重定向或缓存验证 | `301`、`307`、`304` |
| 4xx | 当前请求不能按预期处理 | `400`、`401`、`403`、`404`、`409`、`429` |
| 5xx | 服务端或上游暂时失败 | `500`、`502`、`503`、`504` |

不要用 `200` 包装所有错误，否则代理、客户端和 SLI 无法正确分类。错误响应应提供稳定的机器可读错误码、可安全展示的信息和关联 ID，但不能泄露堆栈、SQL 或内部拓扑。

## 消息边界与内容

明确 `Content-Type`、字符集和可接受编码。代理和应用都要限制请求头、请求体、响应体和解压后大小，防止超大消息、压缩炸弹与内存放大。

流式处理可以降低峰值内存，但下游读取过慢会通过 TCP 流控反向施压。需要设置写入截止时间、最大流持续时间和客户端取消传播。

## HTTP 缓存

`Cache-Control` 定义谁可以缓存、缓存多久和何时必须验证。`ETag` 或 `Last-Modified` 支持条件请求，未变化时返回 `304`。

带认证或个性化内容默认应保守处理。使用 `Vary` 告诉共享缓存哪些请求头影响响应，但过多维度会降低命中率。缓存键必须包含所有影响内容的租户、语言、编码和版本因素，避免数据串用。

## 连接与协议版本

- HTTP/1.1 默认支持持久连接，但每条连接上的并发能力受限。
- HTTP/2 在一条 TCP 连接上多路复用 Stream，并压缩请求头；TCP 丢包仍会影响同连接上的后续字节。
- HTTP/3 基于 QUIC，在 UDP 上提供独立 Stream 和更灵活的连接迁移，但代理、网络和运维工具链需要兼容。

协议升级不能修复慢应用、无上限响应或错误重试。应基于真实 RTT、丢包、连接数量、CPU 和客户端覆盖率比较。

## 生产检查

- 为连接、首字节、完整响应和端到端操作分别设置时间预算。
- 传播请求截止时间和取消，避免客户端离开后服务端继续昂贵计算。
- 正确处理代理转发头，只信任受控代理写入的来源信息。
- 对重定向保留方法的需求选择 `307/308`，不要假设所有客户端对 `301/302` 行为一致。
- 记录方法、路由模板、状态码、响应字节和延迟，不把真实资源 ID 放入指标标签。

使用 `curl -v`、分阶段计时和服务端追踪联合诊断。单个总耗时无法区分 DNS、连接、TLS、排队和应用处理。
