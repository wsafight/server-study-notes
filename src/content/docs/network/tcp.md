description: 理解 TCP 握手、确认、重传、流量控制、拥塞控制和连接关闭，并定位连接异常。
---

TCP 提供有序、可靠的字节流，但不理解 HTTP 请求边界和业务成功。连接建立成功只说明两个 TCP 端点能够通信，不代表应用线程、数据库或下游已经可用。

## 建立连接

典型三次握手为：客户端发送 `SYN`，服务端返回 `SYN-ACK`，客户端发送 `ACK`。握手阶段变慢或失败可能来自：

- DNS 返回错误地址或路由不可达。
- 防火墙、安全组或网络策略丢弃报文。
- 服务没有监听目标地址和端口。
- 监听队列、文件描述符或连接跟踪资源耗尽。
- SYN 或 SYN-ACK 丢失触发重传。

连接超时与连接拒绝不同。拒绝通常说明目标主动返回 RST；超时更可能是报文被丢弃或没有可达响应，但仍需抓包和两端证据确认。

## 可靠传输

TCP 使用序列号和 ACK 确认字节范围。未在预期时间得到确认时会重传；乱序报文会被重组。重复 ACK 和重传是现象，可能由真实丢包、路径变化、接收端停顿或抓包位置造成。

延迟与吞吐同时受影响：

- 接收窗口限制接收端当前可承载的未确认数据。
- 拥塞窗口根据网络反馈限制发送速率。
- RTT 决定反馈周期，长距离链路需要足够窗口才能利用带宽。
- 应用读取过慢会让接收缓冲积压，即使物理网络没有丢包。

不要通过扩大所有 socket 缓冲区直接“修复网络”。更大缓冲可能增加内存并隐藏排队，必须先确认工作集、带宽时延积和应用读写行为。

## 连接关闭

正常关闭通过 FIN 在两个方向分别结束字节流。RST 表示连接被立即复位，未读取数据可能丢失。`TIME_WAIT` 通常由主动关闭方保留，用于吸收旧报文并确保对端能收到最后 ACK。

大量 `TIME_WAIT` 本身不是故障。检查连接创建速率、是否正确复用连接、本地临时端口、NAT 设备和实际错误后再调整架构。

TCP keepalive 用于探测长时间空闲连接，默认周期往往很长。它不能替代带业务语义的请求截止时间或应用心跳。

## 主机侧诊断

```bash
ss -s
ss -lntp
ss -tin dst 192.0.2.10
sar -n TCP,ETCP 1 10
ip -s link
```

`ss -i` 可显示部分连接的 RTT、拥塞窗口、重传和计时器信息，字段依内核版本与拥塞算法变化。两端同时采集比只观察客户端更容易定位方向。

## 抓包验证

在批准范围内使用 `tcpdump` 限定接口、主机、端口、包数和文件大小。握手问题关注 SYN 的方向与重传；传输问题关联序列号、ACK、窗口、重传和应用时间线；关闭问题确认首先发送 FIN 或 RST 的端点。

抓包时钟、虚拟网卡卸载和采集位置会影响看到的校验和与分段，不能把单点捕获直接当作线上真实报文形态。

最终结论应能解释用户延迟、客户端计时、TCP 状态和服务端处理为何在同一时间发生变化。
