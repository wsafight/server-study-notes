TLS 为传输提供机密性、完整性和端点认证。它不能证明应用业务逻辑可信，也不能替代请求级认证与授权。

## 握手建立了什么

现代 TLS 握手大致完成：

1. 客户端发送支持的协议版本、密码套件、随机数、SNI 和 ALPN。
2. 服务端选择参数并返回证书链。
3. 客户端验证信任链、有效期、主机名和证书用途。
4. 双方通过密钥交换派生会话密钥并验证握手完整性。
5. ALPN 决定使用 HTTP/1.1、HTTP/2 等上层协议。

TLS 1.3 减少了握手往返并移除多种旧算法。是否允许旧版本应基于客户端兼容与安全基线，不要仅为了消除连接错误长期放开过时协议。

## 常见证书错误

- 系统时间不正确，证书尚未生效或已经过期。
- 请求主机名不在证书 SAN 中。
- 服务端没有发送必要的中间证书。
- 客户端信任库缺少根证书或使用了错误环境。
- SNI 指向错误虚拟主机，返回了其他站点证书。
- 证书用途、签名算法或密钥强度不被客户端接受。

跳过证书验证会同时失去主机身份保障，使中间人攻击成为可能，不能作为生产修复。

## 诊断握手

```bash
openssl s_client \
  -connect api.example.com:443 \
  -servername api.example.com \
  -showcerts

curl -v https://api.example.com/health
```

检查实际连接地址、SNI、协商版本、ALPN、证书主题、SAN、颁发者、完整链和验证结果。`openssl s_client` 显示连接成功不代表它默认执行了与应用完全相同的主机名验证，测试时应使用目标版本支持的验证参数。

代理链中可能存在多次 TLS：客户端到边缘、边缘到服务、服务到下游。必须确认错误发生在哪一段，以及每段使用的信任库和主机名。

## 双向 TLS

mTLS 让服务端也验证客户端证书，适合服务身份认证或受控设备，但需要管理签发、撤销、轮换和身份映射。证书主题不能未经约束直接映射为高权限账号。

在代理终止 mTLS 后向后端传递身份时，先删除所有外部伪造的身份头，只允许受信代理重新写入，并保护代理到后端的通道。

## 安全轮换

1. 监控证书、根和中间证书的剩余有效期。
2. 在旧证书失效前部署同时兼容的新信任链。
3. 分批替换服务端证书并从真实客户端验证。
4. 保留重叠窗口，避免先移除旧信任导致连接中断。
5. 轮换后清理旧密钥、权限和自动化配置。

证书私钥应使用最小权限存储，不能进入镜像、日志或源码仓库。自动续期成功不代表服务已经重新加载新证书，应监控线上实际呈现的序列号和到期时间。
