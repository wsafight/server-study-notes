---
title: Redis 生产使用守则
description: 从 Key 设计、容量、批量操作、过期、脚本和业务隔离降低 Redis 稳定性风险。
---

Redis 通常位于请求链路的关键位置。使用规范的目标不是追求一套固定阈值，而是限制单次工作的上界、隔离故障，并让容量和延迟可以被观测。

## 设计可管理的 Key

Key 应简洁、可读并包含稳定的业务命名空间，例如：

```text
order:detail:8421
```

避免把隐私数据直接写入 Key。记录 Key 模板、数据结构、负责人、TTL 和预计规模，便于容量评估和故障归属。

## 控制 Big Key

Big Key 会增加网络传输、序列化、复制和删除成本。阈值应根据实例带宽和延迟目标设定，不能把 `10 KiB` 或 `5000` 个元素当成所有业务的统一标准。

- 对大字符串拆分或使用对象存储，只在缓存中保存引用。
- 对大集合分页读取，避免一次返回全部成员。
- 定期通过抽样工具和内存分析发现异常 Key。

## 避免全量扫描

不要在生产大实例上使用 `KEYS *`。遍历 Key 空间时使用 `SCAN`，遍历集合时使用 `HSCAN`、`SSCAN` 或 `ZSCAN`，并控制每批处理时间。`COUNT` 只是提示值，不保证每次返回固定数量。

`HGETALL`、`SMEMBERS` 并非绝对禁止，但只适合已经确认规模有上界的小集合。

## 管理过期时间

- 临时数据应设置 TTL，避免长期占用内存。
- 对大量同时写入的数据加入合理的过期抖动，避免集中失效。
- 缓存失效时应限制回源并发，防止数据库被击穿。
- 不要把 Redis 的淘汰策略当作业务数据生命周期管理。

## 处理 Hot Key

Hot Key 会让单个节点、单核或网络链路成为瓶颈。可以通过本地缓存、只读副本、Key 分片、请求合并或业务层限流降低热点，但分片前要确认一致性和聚合成本。

## 限制批量操作

对 `MGET`、`MSET`、Pipeline、范围查询和批处理同时限制命令数量与总字节数。合适的批次只能通过真实 Value 大小和网络条件压测确定。

批量任务、定时任务和数据回填需要限速、错峰，并与在线流量使用独立的并发预算。

## 安全删除大 Key

小 Key 使用 `DEL` 通常没有问题。删除释放成本较高的大 Key 时优先使用 `UNLINK`，让内存回收在后台进行：

```bash
UNLINK cache:large-result:8421
```

即使使用 `UNLINK`，复制流量和内存释放速度仍需要监控。不要一次提交数量不受控的 Key。

## 减少往返和竞态

使用带选项的单条 `SET` 同时完成写入和过期，避免 `SET` 成功但 `EXPIRE` 未执行：

```bash
SET session:token value EX 1800
```

能使用原生原子命令时，优先于客户端“先读再写”的组合。Pipeline 只减少 RTT，不提供事务原子性。

## 谨慎使用 Lua 和 Functions

脚本在 Redis 中原子执行，复杂或耗时逻辑会阻塞同一执行线程。限制输入规模和循环次数，并准备超时与回滚策略。

使用 `EVALSHA` 可以避免每次传输完整脚本文本，但脚本缓存可能在重启或故障切换后丢失，客户端必须处理 `NOSCRIPT`。Redis Cluster 中，脚本访问的 Key 必须符合相同 slot 等约束。

## 隔离业务与权限

- 不同故障域、容量模型或安全级别的业务应使用独立实例或集群。
- Redis Cluster 只支持逻辑数据库 0；即使是单机或主从模式，也不应把逻辑数据库编号当作可靠的业务隔离。
- 使用 ACL 限制命令和 Key 范围，并为管理操作保留独立账号。
- 不要让其他业务绕过服务接口直接依赖内部缓存结构。

## 持续验证

至少监控命中率、内存、淘汰量、过期量、命令延迟、连接数、网络、复制延迟和持久化状态。任何阈值都应根据实例规格、数据结构和业务 SLO 定期复核。
