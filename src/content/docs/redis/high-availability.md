---
title: Redis 复制、Sentinel 与 Cluster
description: 对比主从复制、Sentinel 和 Redis Cluster，并理解异步复制与故障切换的数据边界。
---

Redis 高可用方案解决的是不同问题：复制提供数据副本，Sentinel 为非 Cluster 部署提供监控与主从切换，Redis Cluster 同时提供 Hash Slot 分片和节点故障转移。它们都需要兼容的客户端和经过验证的失败处理。

## 异步复制的边界

主节点把命令流发送给副本，正常情况下复制是异步的。主节点确认写入后，如果在数据传到副本前故障，新主节点可能缺少已确认数据。

`WAIT` 可以等待指定数量副本确认收到此前写入，但它不把 Redis 变成线性一致系统，也不保证故障切换后一定保留该写入。网络分区、持久化和选主规则仍需单独考虑。

可以通过最少健康副本与最大延迟相关配置限制主节点在复制条件恶化时继续接受写入，但这会用可用性换取更小的数据丢失窗口。

## Sentinel

Sentinel 监控主从实例，通过多个 Sentinel 的判断选举并提升副本。应用不应把主节点地址永久写死，而应通过 Sentinel 感知当前主节点并正确处理连接断开、重定向和重试。

生产部署需要：

- 将 Sentinel 分布在独立故障域，避免一起失联。
- 配置合理的主观下线、客观下线和故障转移超时。
- 验证旧主恢复后作为副本加入，避免双写。
- 在 ACL、TLS 和网络策略下验证 Sentinel 的认证与发现。

## Redis Cluster

Cluster 把键空间划分为 Hash Slot，每个主节点负责一部分 Slot，并可拥有副本。客户端根据 `MOVED` 或 `ASK` 重定向更新拓扑。

多 Key 命令、事务和脚本通常要求相关 Key 位于同一 Slot，可以使用 Hash Tag 显式共置：

```text
order:{8421}:detail
order:{8421}:events
```

Hash Tag 过度集中会形成热点，设计时要同时考虑原子操作和分布均衡。

Cluster 的副本读取可能返回旧数据，扩缩容和迁移 Slot 也会增加网络与延迟波动。客户端必须限制重试次数，刷新拓扑，并避免对非幂等操作盲目重试。

## 容量与故障域

内存容量不能只按主节点 Value 大小计算，还要预留数据结构开销、碎片、复制缓冲、客户端输出缓冲、持久化与故障转移时的 Copy-on-Write。集群失去一个节点后，剩余节点仍应能承载流量和重建副本。

## 演练清单

1. 分别模拟进程退出、机器故障、网络分区和磁盘变慢。
2. 记录检测、选主、客户端恢复和数据追平各阶段时间。
3. 校验已确认写入的实际丢失范围和重复执行情况。
4. 验证发布、扩缩容、证书轮换和密码轮换期间的连接行为。
5. 确认监控在节点角色变化后仍指向正确实例。

高可用不是“有副本”这一静态属性，而是故障检测、选主、数据边界、客户端恢复和日常演练共同形成的能力。
