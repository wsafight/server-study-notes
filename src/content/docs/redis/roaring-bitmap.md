---
title: 理解 Roaring Bitmap
description: 介绍 Roaring Bitmap 的分块容器、集合运算优势和适用边界。
---

普通 Bitmap 用一个 bit 表示一个非负整数是否存在，查询和集合运算很快，但当 ID 空间很大、实际值很稀疏时会浪费大量空间。Roaring Bitmap 通过分块和自适应容器，在压缩率与运算速度之间取得平衡。

## 数据结构

以 32 位整数为例，Roaring Bitmap 通常把整数拆成高 16 位和低 16 位：

- 高 16 位用于找到对应分块。
- 低 16 位存放在该分块的容器中。

容器会根据数据分布选择不同表示：

- **Array Container：** 保存有序整数，适合稀疏分块。
- **Bitmap Container：** 使用固定 Bitmap，适合稠密分块。
- **Run Container：** 保存连续区间，适合大量连续值。

实现会在容器之间转换，让稀疏数据不必承担完整 Bitmap 的空间成本，同时保留按机器字执行 `AND`、`OR`、`XOR` 等集合运算的能力。

## 适用场景

- 用户分群、标签交集和广告受众计算。
- 倒排索引中的文档 ID 集合。
- 大规模去重、权限集合和分析型过滤。
- 需要快速计算交集、并集或基数的整数集合。

## 使用边界

- 元素需要映射为整数 ID；字符串必须先建立稳定映射。
- 数据量很小或非常稠密时，普通数组、Hash Set 或 Bitmap 可能更简单。
- 更新、序列化格式和 64 位支持取决于具体实现，应确认跨语言兼容性。
- Roaring Bitmap 不是 Redis 核心内置类型。需要在应用库、分析引擎或 Redis 模块中使用，并核对模块的持久化与集群支持。

选择数据结构前，应使用真实 ID 分布比较内存占用、交并集耗时和序列化成本。
