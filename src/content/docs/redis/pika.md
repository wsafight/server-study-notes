[Pika](https://github.com/OpenAtomFoundation/pika) 是一个以磁盘为主要存储介质、兼容 Redis 协议和常用数据结构的系统。它基于 RocksDB，目标是降低大容量数据全部驻留内存的成本，而不是在所有场景中替代 Redis。

## 适用场景

- 数据规模明显超过经济可用的内存容量。
- 业务需要 Redis 协议或数据结构，但可以接受更高的访问延迟。
- 重启时不希望把全部数据重新加载到内存。
- 数据访问具有明显冷热差异，并且磁盘吞吐能够满足请求量。

## 主要取舍

优势：

- 大部分数据存放在磁盘，可降低单位容量成本。
- RocksDB 提供持久化、压缩和后台 Compaction 能力。
- 多线程模型可以利用多核处理部分请求。

成本：

- 延迟和吞吐更依赖 SSD、文件系统与 Compaction 状态，不能直接套用 Redis 的容量模型。
- LSM Tree 会产生写放大、空间放大和后台 Compaction 抖动。
- Redis 命令、事务、脚本、过期和复制语义的兼容程度会随 Pika 版本变化。
- 故障恢复、备份和主从切换流程与原生 Redis 并不完全相同。

## 迁移前检查

1. 根据目标 Pika 版本核对业务使用的每一条 Redis 命令。
2. 使用真实 Key 大小、读写比例、TTL 和 Pipeline 批次进行压测。
3. 同时观察 P99 延迟、磁盘带宽、IOPS、写放大和 Compaction。
4. 演练全量迁移、增量同步、故障切换和回滚。
5. 为数据盘预留足够空间，并避免多个高写入实例争用同一块物理盘。

如果业务需要极低延迟且工作集能够稳定放入内存，Redis 通常仍是更直接的选择。Pika 的价值主要体现在容量与延迟之间的另一种权衡。
