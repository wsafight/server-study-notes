缓存引入了来源数据与副本数据之间的时间窗口。设计前应先回答：允许旧数据存在多久、未命中能否回源、来源更新后谁负责失效，以及 Redis 不可用时业务如何降级。

## Cache-Aside

常见读路径是先查缓存，未命中时读取数据库并回填：

1. 读取缓存。
2. 未命中时读取权威数据源。
3. 将结果写入缓存并设置 TTL。
4. 返回结果。

写路径通常先提交数据库，再删除缓存。删除比直接写入新缓存更不容易被并发旧读覆盖，但仍存在数据库提交与缓存删除之间的短窗口。需要根据一致性要求使用重试队列、变更事件或版本号补强。

不要把数据库事务和 Redis 操作假设为一个原子事务。双写失败必须可观测、可重试，并有定期对账方式。

## 防止缓存击穿

热点 Key 到期时，大量请求可能同时回源。常用方式包括：

- 单机或分布式请求合并，只允许一个请求加载，其余等待或返回旧值。
- 逻辑过期并在后台刷新，允许短时间提供明确标记的旧数据。
- 提前刷新热点数据，并为刷新任务设置超时与并发上限。
- 数据库和下游始终保留限流、熔断和隔离能力。

锁本身也可能失败，因此等待者需要超时和降级路径，不能无限阻塞。

## 防止穿透与雪崩

不存在的 ID 被反复查询会绕过缓存。应先做参数校验和授权检查，再考虑短 TTL 的空值缓存或 Bloom Filter。空值缓存必须区分“确实不存在”和“下游临时失败”。

大量 Key 同时到期会造成集中回源。可以在业务允许范围内为 TTL 增加随机抖动，并把预热、批任务和发布错峰。抖动不能替代数据库容量保护。

## TTL 与淘汰策略

TTL 表示业务允许缓存保留的最长时间，淘汰策略则是在达到 `maxmemory` 时选择哪些 Key 被移除，两者不是同一机制。

- 永久 Key 需要明确负责人和容量上限。
- 关键状态不应依赖“尽量不淘汰”的缓存实例。
- 命中率应按业务和 Key 类型拆分，整体高命中率可能掩盖关键接口持续穿透。
- 缓存 Value 中可带数据版本或生成时间，便于识别陈旧数据。

## 更新一致性策略

根据业务选择并记录语义：

- **最终一致：** 提交数据库后异步失效，允许有限旧值窗口。
- **读己之写：** 写入后短时间内强制读来源，或携带版本等待缓存更新。
- **单调读：** 客户端拒绝接受比已见版本更旧的数据。
- **强一致：** 不把 Redis 当作独立缓存副本，改用权威存储或具备一致性协议的方案。

最后通过故障测试验证 Redis 超时、删除失败、重复消息、乱序更新和全量缓存丢失。缓存正确性应由明确的降级与修复流程保证，而不是依靠 TTL 最终“自己变好”。
