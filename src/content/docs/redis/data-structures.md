选择 Redis 数据结构时，先写出需要的原子操作和数据规模，再决定命令。把所有内容序列化进一个 String 看似简单，却会失去局部更新能力，并放大网络、复制和内存成本。

## 常用结构

| 结构 | 典型场景 | 需要警惕 |
| --- | --- | --- |
| String | 缓存对象、计数器、限流状态、位图 | 大对象整值读写、序列化成本 |
| Hash | 字段级读取和更新的小对象 | 字段数无上限、一次 `HGETALL` 返回过大 |
| List | 两端队列、有限长度时间线 | 中间位置访问、可靠消费语义有限 |
| Set | 去重、成员判断、集合运算 | 大集合运算阻塞和临时结果 |
| Sorted Set | 排行榜、按分数索引、延迟队列 | 分数精度、范围返回过多元素 |
| Stream | 消息日志、消费者组 | Pending 消息、修剪策略和重复消费 |

Geo、Bitmap 和 HyperLogLog 建立在特定编码或结构之上，适合位置、布尔状态和近似基数问题，不应为了“省内存”强行替代业务语义。

## 从访问模式出发

例如排行榜需要按分数更新、查询名次和读取区间，可以使用 Sorted Set：

```bash
ZADD leaderboard 9820 user:42
ZREVRANK leaderboard user:42
ZREVRANGE leaderboard 0 99 WITHSCORES
```

如果只需要按 ID 读取用户资料，则 Hash 或序列化 String 更直接。是否选择 Hash 取决于是否需要字段级原子更新、对象大小、压缩编码和客户端序列化方式。

## 复杂度不等于实际延迟

命令文档中的 `O(1)`、`O(log N)` 描述算法随元素数量增长的趋势，不包含网络传输、编码、内存分配、复制和持久化成本。返回 100 MB 的 String 即使命令查找是 `O(1)`，也会明显阻塞链路。

对集合命令同时限制：

- Key 包含的元素总数。
- 单元素和总字节数。
- 单次返回或修改的元素数量。
- Pipeline 或事务中的累计工作量。

需要遍历时使用 `SCAN` 系列命令并接受弱一致遍历语义。扫描期间元素可能重复出现，也可能因并发变化而错过，调用方应允许去重和重试。

## 原子性边界

单条 Redis 命令原子执行，但多个命令之间可能被其他客户端插入。优先使用带选项的原生命令，例如：

```bash
SET session:42 payload EX 1800 NX
```

确实需要组合逻辑时，可以使用事务、Lua 或 Functions，但它们在服务端执行期间仍要限制循环和输入规模。长脚本会阻塞其他命令。

## 建模清单

为每类 Key 记录命名模板、数据结构、TTL、元素上限、Value 上限、读写 QPS、失败后是否可重建和负责人。上线前用真实分布压测，不要只用平均对象大小估算容量。
