---
title: 使用 Redis 实现分布式锁
description: 使用唯一令牌、原子释放、租约续期和 fencing token 控制分布式任务并发。
---

Redis 锁本质上是有过期时间的租约。它可以减少重复工作，但不能保证持有者在整个业务操作期间始终拥有唯一执行权：进程暂停、网络延迟或故障切换都可能让租约过期，而旧持有者仍继续运行。

## 获取锁

使用单条 `SET` 同时完成不存在判断和过期设置，并为每次获取生成不可预测的唯一令牌：

```bash
SET lock:invoice:8421 2f51b... NX PX 30000
```

只有返回成功的客户端才持有租约。超时时间应覆盖正常操作并留有余量，但不能无限长；长任务需要安全续期或拆分。

## 只能释放自己的锁

不能先 `GET` 再 `DEL`，两条命令之间锁可能已经过期并被其他客户端获取。使用 Lua 原子比较令牌后删除：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

续期也必须比较令牌后原子延长 TTL。客户端失去与 Redis 的连接、进程长时间停顿或续期失败时，应假定自己已经失去锁。

## 过期持有者问题

假设客户端 A 获得 30 秒锁，随后暂停 40 秒。锁过期后客户端 B 获得锁并完成写入，此时 A 恢复并继续写入，就会覆盖 B 的结果。即使释放脚本正确，也无法撤销 A 对外部系统的迟到操作。

对不能容忍迟到写入的资源，应使用单调递增的 fencing token：每次获得租约同时拿到更大的序号，下游只接受大于已见序号的请求。仅有随机锁令牌不能提供这个顺序保证。

## 失败与重试

- 获取失败时使用有限次数、带抖动的退避，避免所有等待者同时重试。
- 为业务操作设置独立超时，锁 TTL 不是请求超时。
- 释放失败记录指标和上下文，等待 TTL 只是兜底。
- 任务必须幂等，或通过唯一约束、状态机和请求号拒绝重复副作用。
- 监控获取延迟、持有时间、续期失败和过期后仍运行的任务。

## 何时不该使用 Redis 锁

如果资源只存在于关系数据库中，唯一约束、条件 `UPDATE` 或行锁通常更直接。涉及资金、所有权或主节点选举等严格正确性问题时，应使用具备共识和 fencing 语义的协调系统，或让权威存储验证每次写入顺序。

多 Redis 节点锁算法的安全性取决于时钟、网络和故障假设。采用前必须写清系统模型和可接受风险，不能因为使用多个节点就直接宣称获得强一致分布式锁。
