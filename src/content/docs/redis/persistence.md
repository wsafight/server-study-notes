---
title: Redis RDB 与 AOF 持久化
description: 理解快照、追加日志、fsync、重写与恢复的性能和数据丢失边界。
---

Redis 以内存提供服务，RDB 和 AOF 用于在进程或机器重启后重建数据。持久化策略应从 RPO、恢复耗时和写入负载出发，复制副本不能替代独立备份。

## RDB 快照

RDB 在某个时间点生成紧凑的数据文件，适合备份、传输和较快加载。后台保存通常通过派生子进程遍历数据，父进程继续处理请求。

需要关注：

- 两次快照之间的写入在故障时可能丢失。
- fork 本身和页表复制会产生延迟，数据集越大越需要监控。
- 保存期间发生的写入会触发 Copy-on-Write，增加额外内存占用。
- 磁盘带宽不足会同时影响持久化、AOF 和其他服务。

## AOF 追加日志

AOF 记录能够重建数据集的写命令。`appendfsync` 决定刷盘策略：

- `always`：每次写入都请求同步，耐久性更强但延迟和吞吐成本最高。
- `everysec`：通常每秒同步一次，是常见折中，故障时仍可能丢失最近约一段时间的数据。
- `no`：交给操作系统安排写回，数据丢失窗口更难控制。

具体耐久性还取决于操作系统、文件系统、虚拟化和存储设备，不能把配置值当作硬件故障下的绝对承诺。

AOF 会持续增长，需要重写为等价但更紧凑的状态。重写同样涉及 fork、Copy-on-Write、临时空间和最终文件切换，应在真实写入速率下评估。

## 同时使用 RDB 与 AOF

同时启用可以兼顾恢复速度、备份便利和更小的数据丢失窗口，但也会叠加 CPU、内存和磁盘成本。Redis 重启时通常优先使用更完整的持久化数据源，具体规则应以目标版本配置为准。

不要在不理解后果时删除损坏的持久化文件并空实例启动。空数据可能继续复制到其他节点，扩大事故。

## 监控与故障处理

从 `INFO persistence` 持续观察最近保存状态、AOF 状态、重写进度和错误：

```bash
redis-cli INFO persistence
```

持久化失败后，Redis 是否拒绝写入取决于配置。告警必须覆盖后台保存失败、AOF 写入错误、磁盘空间、fork 耗时和 Copy-on-Write 峰值。

## 备份与恢复演练

1. 将 RDB/AOF 复制到与生产不同的权限和故障域。
2. 对备份加密、校验并执行保留与不可变策略。
3. 定期恢复到隔离实例，验证 Key 数量、抽样值、TTL 和业务汇总。
4. 记录加载时间、峰值内存和客户端恢复步骤。
5. 在升级 Redis 或修改持久化策略后重新演练。

缓存数据如果可以从来源重建，也要验证回源速率限制。一次空缓存启动可能把数据库压垮，恢复设计应包括预热、限流和逐步放量。
